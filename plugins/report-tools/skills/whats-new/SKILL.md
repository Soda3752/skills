# What's New 報告產生 Skill

## 目標

從 git history 中擷取兩個版本之間的所有變更，派遣多個平行 agents 深度分析每個 commit，
最終整合成一份**純粹從使用者體驗角度**描述的繁體中文 What's New 報告，
完全不提程式碼、函數名稱、變數、檔案路徑等技術細節。

---

## 步驟一：解析版本範圍

使用者會提供兩個版本號，例如 `0.1.5 0.1.6`（舊版本在前，新版本在後）。

用以下策略找出對應的 git commit 範圍（依序嘗試）：

1. **直接 git tag 比對**：執行 `git tag` 列出所有 tag，找包含版本號的 tag（例如 `v0.1.5`、`0.1.5`、`release/0.1.5`）
2. **從 commit message 找版本起始點**：若找不到 tag，在 commit log 中搜尋「更新.*版本.*{舊版本號}」或「version.*{舊版本號}」的 commit，以該 commit 作為起始點
3. **若兩個版本號都找不到對應 tag 或 commit**：告知使用者並請他確認正確的版本範圍

找到範圍後，執行：
```bash
git log {舊版本範圍}..{新版本範圍} --oneline --no-merges
```

取得兩版本間的完整 commit 列表。

---

## 步驟二：分類 commits

將所有 commits 依照 commit message 前綴分類：

| 分類 | 前綴關鍵字 | 報告標題 |
|------|-----------|---------|
| 新功能 | `feat` | 新增功能 |
| Bug 修復 | `fix` | Bug 修復 |
| 基礎建設 | `ci`、`chore`、`build`、`infra` | 基礎建設 |
| 效能優化 | `perf`、`refactor` | 效能與優化 |

**只有**純版本號 bump 的 commit（例如 `chore: 更新應用版本至 X.X.X`、`fix(build): 更新版本號至 X.X.X`）才可跳過。

**禁止主觀判斷跳過任何其他 commit**，即使 commit message 看起來是「開發者工具」、「內部功能」、「Debug 用途」。所有非版本 bump 的 commit 都必須分析並納入報告。若功能僅限內部使用，在報告標題後加上 `*(內部工具)*` 標注即可，但不得省略。

---

## 步驟三：平行派遣 agents 分析每個 commit

**對每一個需要分析的 commit，各自派遣一個獨立 agent**，所有 agents 同時執行（parallel）。

每個 agent 的任務指示如下：

```
你是一個軟體發布說明撰寫專家。請分析以下 git commit，
從「使用者體驗」角度撰寫說明。

Commit SHA: {sha}
Commit Message: {message}

請執行：git show {sha} --stat

根據 commit 內容，以繁體中文回答：
1. 問題症狀（如果是 bug fix）：使用者過去遇到什麼困擾？畫面上看到什麼異常？
   或 功能說明（如果是新功能）：這個功能能讓使用者做什麼？帶來什麼價值？
2. 修復/新增後的效果：使用者現在的體驗如何改善？

硬性規定：
- 完全不提程式碼、函數名稱、變數名稱、檔案路徑、API、Class 名稱
- 使用一般使用者能理解的語言
- 每個描述 2-5 句話，簡潔精確
- 只回傳分析結果，格式：
  標題: {一行簡短標題}
  描述: {詳細說明}
  平台標注: {若限定 iOS 或 Android 才影響，標注 [iOS] 或 [Android]，否則留空}
```

---

## 步驟四：整合並輸出報告

收集所有 agents 的回傳結果後，整合成以下格式的報告：

```markdown
# {專案名稱} — What's New ({舊版本} → {新版本})

> 發布日期：{今日日期 YYYY-MM-DD}

---

## 新增功能

### {功能標題} {平台標注}
{功能描述}

（依此類推...）

---

## Bug 修復

### {修復標題} {平台標注}
{問題症狀說明}
{修復後效果}

（依此類推...）

---

## 基礎建設

（僅在有相關 commit 時才顯示此段落，用一兩句話簡述對團隊或發布流程的改善）
```

報告儲存規則：
- 路徑：`{當前工作目錄}/.claude/report/{YYYY_MM_DD}/whats_new_{舊版本}_to_{新版本}.md`
- 版本號中的 `.` 改為 `_`（例如：`whats_new_0_1_5_to_0_1_6.md`）
- 若目錄不存在則自動建立

---

## 注意事項

- 若某個 commit 的描述語意不清，agent 應根據 `git show` 看到的實際變更推斷使用者影響，而不是複製 commit message
- `chore`、`ci`、`build` 類的 commit 通常是幕後建設，在「基礎建設」段落用簡短一句帶過即可，不需要詳細分析
- 同一個功能模組若有多個 commit（例如先 feat 再 fix 同一功能），在報告中合併為同一條說明，避免重複
- 最後報告呈現給使用者看的同時，也提示報告儲存的完整路徑
