# Jira 票券工作流

**只要是照著某張 Jira 票做的工作，票券狀態要跟著實際進度走，不必等使用者交代。** 看板要能隨時看出現在在哪張票、做到哪個階段——不要整張票悶頭做完才一次更新。

這份文件只寫「行為」。站台、專案 key、transition id 這些值一律不寫死在這裡，全部去讀 `.claude/jira-workflow.json`——因為同一套行為要能套在不同專案上，而那些值換專案就換。

## 設定檔

推任何狀態、寫任何註解之前，先讀 `.claude/jira-workflow.json`：

```json
{
  "site": "…atlassian.net",
  "projectKey": "…",
  "transitions": {
    "todo": "…", "inProgress": "…", "inReview": "…",
    "block": "…", "apiRequire": "…", "done": "…"
  },
  "verified": { "inReview": false },
  "extraStatuses": [{ "id": "…", "name": "…" }],
  "apiRequireLabel": "api-require",
  "ticketSource": "branch+jql",
  "branchPattern": "([A-Za-z]+-[0-9]+)"
}
```

- `site` 直接當 `cloudId` 參數傳給 MCP，不需轉 UUID。
- `verified` 裡標 `false` 的 transition 是 init 當時沒能實查驗證的。這種 id 有猜錯的可能，所以每次要用到它之前，先跑下面的三步流程確認。
- `extraStatuses` 是這個專案多出來、不屬於下面六個核心狀態的狀態欄。**工作流不會自動推票進去**——它們是專案自己的用法，要用得由使用者明講。列在這裡只是讓你知道看板上還有這些欄。

## 推狀態的三步流程

Jira MCP 走 `claude_ai_Atlassian`。任何狀態轉換都照這個順序，不要拿設定檔的 id 直接送：

1. 讀 `.claude/jira-workflow.json` 取 `site` / `transitions`
2. `getTransitionsForJiraIssue` 查這張票**當下**可用的轉換
3. `transitionJiraIssue`

第 2 步不是多餘的。transition id 綁在 workflow scheme 上，而且票在不同狀態下可用的轉換不同——設定檔裡那個 id 可能根本不在當前可用清單裡。實查一次就知道該送哪個，也順便抓到設定檔已經過期。**若實查結果與設定檔不符，以實查為準，並回報使用者設定檔該更新哪一欄。**

## 當前在哪張票

推狀態的前提是知道票號。票號的來源有優先序，別靠對話裡「剛剛提過」的記憶——跨 session 接手時那個記憶就沒了。

**主要來源：git 分支名。** 用 `branchPattern` 從分支名抽票號：

| 分支 | 抽出 |
| --- | --- |
| `fix/proj-8-9-api-path-and-codes` | PROJ-8、PROJ-9 |
| `feature/PROJ-49-idle-warning` | PROJ-49 |
| `main` / `develop` / 無票號分支 | 抽不到 |

**輔助交叉比對：JQL 實查。** 抽到票號後，另外查一次「`project = <projectKey>` AND `status = 進行中` AND `assignee = currentUser()`」。兩邊對不上時就回報，不要默默選一邊：

- 分支有 PROJ-8，但 PROJ-8 不在進行中 → 這張票的狀態沒跟上，可能該推 `inProgress`
- Jira 有票在進行中，但不在分支名裡 → 可能有票被遺忘在進行中，或現在做的其實是別的事

**抽不到票號時必須問使用者「這輪對到哪張票？」，不得猜、不得默默跳過推票。** 猜錯票號會把狀態推到別人的票上，比不推更糟；而默默跳過會讓看板停留在錯誤狀態，那正是這份工作流要解決的問題。

## 三個必推的時點

| 時點 | 推到 | 說明 |
| --- | --- | --- |
| **開始動工前** | `transitions.inProgress` | 規格確認完、要下第一個編輯動作之前就推，不是寫完才補。若卡在規格釐清或調查階段還沒動碼，也先推——調查本身就是這張票的工作。 |
| **程式完成、進入驗證** | `transitions.inReview` | 編譯過了、開始跑測試／實機驗證／自我 review 時推。這個階段票上發生的事最多（驗收逐條核對、發現邊界情境），狀態要看得出來。 |
| **驗收完成** | `transitions.done` | 驗收條件逐條核完、commit 完成後推。**推之前必須先加實作紀錄註解**（見下），不要只改狀態。 |

若一張票分多個 session 做，每次重新接手時先確認狀態仍正確，別讓票停在 `inProgress` 卻其實早就進驗證了。

## 被擋住的時候：`block` 還是 `apiRequire`

兩個都是「卡住」，差別在誰能解。判準是一句話：

> **要解這個阻塞，得有人動後端嗎？**

| 答案 | 推到 | 典型情形 |
| --- | --- | --- |
| **是** | `transitions.apiRequire`，並加上 `apiRequireLabel` 這個 label | API 還沒提供、契約不完整、錯誤碼未定義、回傳缺欄位 |
| **否** | `transitions.block` | 被另一張票擋住、缺實機／裝置、等設計稿、等使用者決策 |

加 label 的意義是讓所有後端缺口票能用一條 label 查詢聚合起來交給後端，而不是散在看板各處。

兩者都要在註解寫清楚**卡在哪、需要誰做什麼**——狀態欄只說明「停住了」，註解才說明「怎麼才能動」。

## 註解怎麼寫

票上的註解有兩種讀者，**寫法完全不同**：

| 讀者 | 要的東西 | 寫在哪 |
| --- | --- | --- |
| 人（你自己、PM、下週接手的同事） | 這張票到底改變了什麼、能不能信、還有什麼沒做 | 註解正文 |
| Agent（續跑的 loop、盤點 skill、下一張票的實作者） | 可直接取用的欄位：commit、檔案、驗收結果、地雷 | 末尾的 YAML 區塊 |

**兩者不要混寫。** 混在同一段自由文裡的結果，是為了同時滿足兩邊而寫得很抽象——人看不出實際做了什麼，agent 也解析不出東西。分開寫之後，正文可以講人話，YAML 可以講精確。

### 寫給人看的部分：九條硬規則

這幾條是可以逐條檢查的，不是方向性建議。寫完自己過一遍。

1. **結論寫在第一句。** 先講這張票改變了什麼，再講怎麼做到的。不要鋪陳背景。
2. **一句一件事，句子不超過 25 字。** 超過就斷句。
3. **動詞開頭，主動語態。** 寫「改用串流讀取大檔」，不要寫「針對大檔的讀取方式進行了調整」。
4. **同一個東西全篇用同一個詞。** 決定叫「票」就整篇叫票，不要在議題、card、ticket 之間換。換詞會讓讀者以為你在講不同東西。
5. **禁用模糊修飾詞。** 這幾個一律不准出現：大致上、基本上、原則上、應該、若干、相關處理、進行優化、完善、健全、做了一些調整。要嘛給具體對象，要嘛給數字。
6. **數字要有基準與單位。** 寫「128 項測試全數通過」，不要寫「測試都過了」。
7. **提到檔案或函式時，先講它負責什麼。** 讀者不一定看過這份程式碼。寫「匯出流程的進入點 `ExportService`」，不要只丟一個類別名。
8. **驗收結果只用四個固定詞：通過／部分通過／未實測／沒做。** 不要自創「基本通過」「應該沒問題」——這種詞會讓日後查帳的人無法判斷當時到底驗了沒。
9. **「沒驗」就寫沒驗。** 不要因為程式看起來對、或因為別人回報完成，就升級成通過。註解是給未來的人看的，**寫錯比留白傷害大**。

正反例：

| 不要這樣寫 | 改成這樣 |
| --- | --- |
| 完成了相關處理，功能已可正常運作 | 匯出功能現在可處理 500MB 以上的檔案，不再中途失敗 |
| 針對效能問題進行了優化 | 匯出 10 萬筆資料的時間從 42 秒降到 6 秒 |
| 驗收條件皆已滿足 | AC1 通過、AC2 部分通過（只驗了 iOS）、AC3 未實測（需真機藍牙） |
| 修改了若干檔案以支援新流程 | 改了 3 個檔案：進入點加分頁參數、資料層改串流、測試補 2 個案例 |

### 實作紀錄註解（推 `done` 前必做）

用 `addCommentToJiraIssue`，`contentFormat: "markdown"`，繁體中文。照這個形狀寫：

````markdown
## 完成：<票號> <票標題>

<一句話結論：誰現在可以做到什麼。>

**做了什麼**
- <動詞開頭，一到四條，講改變不是講檔案>

**驗收對照**
| # | 驗收條件 | 結果 | 依據 |
| --- | --- | --- | --- |
| 1 | <條件原文> | 通過 | <實際怎麼驗的> |
| 2 | <條件原文> | 未實測 | <為什麼驗不到> |

**決策與取捨**
- <與票券原始描述不同的地方> → <為什麼這樣改>

**風險與未驗證**
- <未驗的部分，以及誰該接手驗>
- <已知限制、留下的技術債>

---
### 給 Agent 的結構資料

```yaml
ticket: PROJ-24
status: done
branch: feature/proj-24-export-stream
commits: [a1b2c3d]
files:
  - src/export/ExportService.kt
acceptance:
  - id: AC1
    result: pass
    note: 500MB 檔案實測通過
  - id: AC3
    result: unverified
    note: 需真機藍牙
verification:
  - cmd: ./gradlew test
    result: pass
    tests: 128
unverifiable: [真機藍牙連線]
decisions:
  - what: 改用串流而非全載入
    why: 全載入在 500MB 就 OOM
pitfalls:
  - tried: 調大 heap size
    failed_with: "java.lang.OutOfMemoryError: Java heap space"
followups: [PROJ-51]
unblocks: [PROJ-25]
```
````

**這裡與 Linear 版的唯一差異：結構資料不要用 `<details>` 摺疊。** Jira 的註解會被轉成 ADF，HTML 的 `<details>` 沒有對應節點，轉換結果不保證是摺疊區——可能整段變純文字，也可能被吃掉。用分隔線加小標題是穩的。

YAML 的規則：

- **受控值，不要自由發揮。** `status` 只有 `done` / `in-review` / `blocked` / `api-require`；`result` 只有 `pass` / `partial` / `unverified` / `skipped`，與正文表格的四個中文詞一一對應。
- **路徑、指令、錯誤訊息一律保留英文原文。** 這一區存在的意義就是日後 grep 得到，翻成中文就廢了。
- **`pitfalls` 的 `failed_with` 要原始錯誤訊息，不要摘要。** 「建置失敗」對下一個人毫無用處，完整訊息才能讓他三秒認出是同一個坑。**但貼上去之前先遮掉 token、密碼與內部主機名**——Jira 註解的可見範圍通常比 repo 大，這條比「保留原文」優先。遮蔽時只換掉敏感片段，錯誤訊息的其餘部分照留。
- **沒有內容的欄位整段省略**，不要留空陣列充數。
- 正文與 YAML **不准互相矛盾**。正文說未實測，YAML 就不能寫 `pass`——矛盾時以正文為準，但那代表你寫錯了一邊。

### 正文的排序：結論在前，證據下沉

**這是註解最容易寫壞的地方，而且寫壞的方式永遠是同一種**：把工作的**時間順序**當成寫作順序——先交代 commit、再交代跑了哪些閘門、再交代複查發現，最後才講「所以這張票做出了什麼」。讀者要的東西全被推到最後面。

正文**只回答三個問題，而且按這個順序**：

| 順序 | 問題 | 內容 |
| --- | --- | --- |
| 1 | **這張票改變了什麼？** | 成果，帶數字。使用者或系統現在多了什麼能力 |
| 2 | **能不能信？** | 複查抓到什麼真問題、怎麼處置的 |
| 3 | **還缺什麼？** | 未驗證清單、已知限制 |

其餘全部往結構資料區沉。判準只有一句話：

> **讀者不追問「你怎麼知道」就不需要的東西，就不該在正文。**

照這條，這些一律下沉——它們是證據，不是結論：commit hash 的演進過程、逐條閘門的輸出、測試斷言數變化、被排除的閘門與盲區評估、版面／效能的完整量測、複查發現的逐條推導。

正文每段也有條數上限，超過就是還沒收斂完：

| 段落 | 上限 |
| --- | --- |
| 結論 | 1 句 |
| 做了什麼 | 4 條 |
| 複查抓到的真問題 | 每條 1 行（抓到什麼 → 怎麼處置），完整論證下沉 |
| 決策與取捨 | 每條 1 行（決定 → 一句理由），完整推導下沉 |
| 風險與未驗證 | 不限，**這段永遠不准為了精簡而砍** |

### 不要寫進票裡的三類東西

| 別寫 | 為什麼 | 該去哪 |
| --- | --- | --- |
| 流程自省（「我派工時漏了一條閘門」） | 與這張票的產出無關，只與工作方式有關 | loop 的 log／HANDOFF |
| 方法論說明（「跑異質來源複查是關鍵一步」） | 讀者要的是結果，不是你的作業程序 | 刪掉，或進 skill 文件 |
| 沒打穿的正面背書（「複查核對了 A、B、C 都沒問題」） | 沒發現問題等於沒有資訊。列三段只會讓真正的發現被埋掉 | 壓成一句「另核對 N 項無發現」 |

### 實作者要留下思考軌跡

實作紀錄註解如果由**實際動手的那個角色**寫（subagent、pane、Codex），它比任何轉述都珍貴的是三件事——這三件事一旦沒寫下來就永久消失，因為 worktree 會被移除、context 會被壓縮：

```markdown
**我考慮過但沒選的做法**
- <方案> → <為什麼不選，一句話>

**我撞到的牆**
- <試了什麼> → <原始錯誤訊息> → <改用什麼>

**我沒驗到的**
- <哪一條> → <為什麼驗不到，不是「沒時間」而是具體障礙>
```

「考慮過但沒選」是**最容易被省略、也最貴的一段**。下一個人接手時，第一個冒出來的念頭往往正是你已經評估過並否決的方案；沒寫下來，他就要重走一次那條死路。

寫的時候用第一人稱、講當下的判斷，**不要事後修飾成好像一開始就想對了**。

### 其他註解也適用同一套規則

九條硬規則適用**所有**寫進票裡的註解，不只實作紀錄。各類註解的重點差異：

| 類型 | 第一句要講 | 需要 YAML 區嗎 |
| --- | --- | --- |
| 進度／卡關 | 現在卡在什麼、需要誰做什麼 | 不用 |
| 整合紀錄（合併後） | 程式碼已經進了哪個分支 | 要，至少 `commits` 與 `verification` |
| 解鎖通知（下游票） | 你現在可以直接用什麼 | 不用，但要具體到檔案路徑 |

### 有實作者與整合者兩個角色時：寫兩則，不要一則

實作與整合分屬不同角色時（worktree 裡的 subagent／pane 實作，主控負責審碼與合併），**票上要有兩則註解，不是主控寫一則轉述**：

| 誰 | 寫什麼 | 標題 |
| --- | --- | --- |
| 實作者 | 實作紀錄 + 思考軌跡（考慮過但沒選、撞到的牆、沒驗到的） | `## 實作紀錄（<角色> · <票號>）` |
| 整合者 | 整合與複查紀錄：**收斂 + 加註 + 修正**，不是重述 | `## 整合與複查（主控）` |

**主控那則的第一句不是「我做了什麼」，是「這張票現在是什麼狀態」**——已經進了哪個分支、能不能信。接著才是它獨有的三件事：我對實作者判斷的修正、複查抓到的真問題、**仍未驗證（原樣保留，不因合併成功就升級成通過）**。

**兩則都寫，資訊不會重複——它們回答的是不同問題。** 實作者那則回答「當時是怎麼想的」，主控那則回答「現在能不能信」。轉述一定會流失第一人稱的判斷過程，而那正是日後最有用的部分。

**實作者不得改票券狀態、不得動 labels、不得碰其他票**——那仍然是主控的職責。留言權與狀態權分開，看板的因果關係才追溯得到。

## 收票後必做：解開被這張票擋住的其他票

**每次把一張票推到 `done` 之後，主動往下游檢查一輪，不要等使用者問。**

1. 從剛完成那張票的 `issuelinks` 找出所有 `blocks`（outward）的下游票。
2. 對每一張下游票，查它**自己的**所有 `is blocked by`（inward）連結，逐一確認狀態。
3. **所有** blocker 都已完成 → 這張票解鎖了，把它從擋住的狀態推到 `transitions.todo`（除非它已經在進行中或更後面的狀態，那就別動）。
4. 還有 blocker 沒完成 → 維持原狀不動，並在回報中寫清楚它還卡在哪張票。

解鎖時在下游票加一則簡短註解，說明是被哪張票（票號 + 標題）解開的，讓看板上看得出因果。

**判斷依據一律是實際查到的 blocker 狀態，不是推測。** 一張票只被一張票擋住不代表就是剛完成的那張——每次都要實查 `issuelinks`。

除了「blocker 全清 → 解鎖」這一種情形，**不要改動其他票的狀態**。要改別的（重排優先序、關掉重複票、改 Epic 歸屬）先問使用者。

## 「更新 Jira」的預設含義

使用者只說「更新 Jira」時，預設是三件都做：

1. 推狀態到當前階段該有的位置
2. 加實作紀錄註解
3. 檢查下游解鎖
