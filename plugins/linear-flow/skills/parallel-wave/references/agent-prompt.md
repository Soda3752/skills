# 派工指令模板

每個 subagent 一份，用 `subagent_type: "claude"`（需要完整工具）。**所有 Agent 呼叫放在同一則訊息**才會平行。

`name` 參數用票號（`proj-97`），閒置通知才看得出是誰。

---

## 模板

```
你負責在獨立 git worktree 中完成 Linear 票 **<TICKET>「<標題>」**。

## 工作區（不要離開這裡做修改）
- worktree：`<worktreeRoot>/<dir>`
- 分支：`<gitBranchName>`（已建好，基於 <base> `<hash>`）
- 主 repo `<mainRepo>` **唯讀**：只用來讀 `<specDocsRoot>` 規格（該目錄被 gitignore，不在 worktree 裡）。禁止在主 repo 做任何修改、commit、checkout。
- **建置設定檔已幫你複製好**（<untrackedSetupFiles>），不必自己處理。

## 第一步
1. Linear MCP `get_issue({ id: "<TICKET>" })` 讀完整描述——那是規格，逐條照做。
   （若票上有既有註解，一併 `list_comments` 讀過，解鎖註解常寫著現在可以直接用什麼。）
2. 讀規格文件：<相關規格檔絕對路徑與章節>
3. 讀 `<mainRepo>/CLAUDE.md` 專案守則。<若守則與實際環境有出入，在此明講>

## 可直接用的既有基礎
<列出前幾波已完成、現在可取用的元件／型別／測試工具，附路徑>
**不要重寫或改動這些**，直接用。

## <票券特定的關鍵約束>
<例如：已知的裝置限制、必須照抄的既有行為、絕對不能自作主張「修好」的缺陷>

## 平行作業注意
另有 <N> 個 agent 同時在做 <其他票號>。
<衝突紀律：哪些檔不要碰；若必須改共用清單，加在最末端並用註解標區塊、只改最小必要行數、不要順手重排>
若非動 <依賴宣告檔> 不可，在最終回報中明確列出。

## 環境與驗證
```bash
cd <worktreeRoot>/<dir> && \
<env> <verifyCommand> > /tmp/<TICKET>-verify.log 2>&1; echo "EXIT=$?"; tail -40 /tmp/<TICKET>-verify.log
```
建置輸出很大，**一律重導到 log 再 tail**，不要讓輸出直接灌進 context。

- <verifyCommands 逐項，說明哪些必須綠燈>
- **跑完讀測試結果檔確認測試真的有執行**（`<testResultsGlob>`，`tests="N"` 不是 0）。測試沒被執行時建置一樣會成功，這是假綠燈的主要來源。
- <哪些驗收條件本機驗不到，要誠實標記>

## 完成後
1. commit（<commitConvention>）。結尾加：
   `Co-Authored-By: <co-author>`
2. **不要 push 遠端、不要合併回 <base>、不要動 <base> 分支。**
3. Linear MCP：
   - `save_comment({ issueId: "<TICKET>", body: ... })` 實作紀錄。**先讀 `<主 repo 路徑>/.claude/linear-workflow.md` 的「註解怎麼寫」章節，照那個模板寫**（<commentLanguage> Markdown，用真正換行不要寫 `\n`）。標題寫 `## 實作紀錄（agent · <TICKET>）`。正文給人看，**結論在前、證據下沉**：一句話結論（帶數字）、做了什麼（最多 4 條）、驗收逐條對照表（四個固定詞：通過／部分通過／未實測／沒做）、**我考慮過但沒選的做法**（方案 → 一句理由）、**我撞到的牆**（試了什麼 → 原始錯誤訊息 → 改用什麼）、**我沒驗到的**（哪一條 → 具體障礙）。`<details>` 摺疊區放 YAML 結構資料與逐條閘門輸出，`verification` 要有測試實際執行數。

**「考慮過但沒選」這段不要省——它是你留給下一個人最貴的東西**，沒有它，接手的人會重走一次你已經否決過的死路。用第一人稱寫當下的判斷，不要事後修飾成一開始就想對了。**沒驗的不要寫成通過。**
   - `save_issue({ id: "<TICKET>", state: "<states.inReview.id>" })` 推 In Review。
   - 不要推 Done（合併後由主 agent 推），不要改其他票。

## 回報給我
commit hash、改動檔案清單、驗證的實際結果（含測試數量）、<是否碰共用檔及改了哪幾行>、沒做完或不確定的地方。誠實回報失敗，不要粉飾。
```

## 為什麼每一段都要有

**讓 agent 自己 `get_issue`**：票是唯一權威，複製 description 進指令既浪費你的 context，又會在票被修改後失準。

**主 repo 唯讀**：規格文件常放在 gitignore 的目錄（vault、docs、design），worktree 裡沒有，只能回主 repo 讀。但同時必須嚴禁在那裡改——併發寫主 repo 是災難。

**告知建置設定檔已複製**：否則 agent 撞到那個看不出真因的錯誤時，會花很久往錯的方向查。

**列出「可直接用的既有基礎」**：前幾波的成果 agent 不會自動知道。沒講就會重造輪子，或自己又寫一個功能重疊的元件。

**「不要重寫或改動這些」**：地基型別特別容易被「順手改好一點」，而那會破壞其他票的假設。

**票券特定的關鍵約束**：像「不准修掉既有缺陷」這種反直覺要求，一定要講明白**為什麼**（例如：修掉會讓兩個平台算出不同結果）。只寫禁令而不給理由，聰明的 agent 會判斷你錯了然後照自己的想法做。

**平行作業注意**：agent 預設以為自己是唯一在動這個 repo 的人。知道有鄰居才會自我克制、才會在回報裡主動說「我碰了共用檔」。

**重導 log**：建置輸出動輒數千行，直接進 context 會讓 agent 之後什麼都做不了。

**讀測試結果檔**：這條是實戰教訓——「BUILD SUCCESSFUL」不等於測試有跑。假綠燈比失敗更糟，因為它會被當成證據。

**不准 push／合併／動 base／改別的票**：整合是主 agent 的職責。放手讓 agent 碰，會出現併發寫 base、垃圾 merge commit、把別人的票推錯狀態。

**誠實標未驗證**：註解是寫給未來的人看的。把沒驗的寫成通過，日後有人據此做決策會踩雷。明講「這條本機驗不到」反而讓人知道該補什麼。

**回報要求含測試數量與共用檔**：這兩項直接決定你整合時的審查重點與合併順序。
