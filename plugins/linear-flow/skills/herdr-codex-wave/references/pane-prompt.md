## 為什麼是散文而不是 XML

`codex exec` 的一次性背景 job 場景下，XML 區塊有幫助（機器讀、無互動、要求結構化）。

**互動 pane 不一樣**：Codex 在 pane 裡是連續對話，會反覆讀你這則訊息當作整輪的憲章。實測散文加標題效果好，因為理由講得出來——而理由是它自己判斷邊界情境時唯一能依據的東西。**指令裡每一條限制都附上「為什麼」**，它遇到模板沒寫到的情況時才知道往哪邊靠。

## 做完之後：起本地服務、開測試頁、寫人工驗收清單
閘門全綠、commit 完成之後，**在使用者面前把畫面打開**。本專案瀏覽器層沒有任何自動守門，
你寫的清單是這張票唯一的視覺驗證來源。

你被分配到的 port 是 <PORT>，**只准用這個**（同一波還有別的 pane，撞 port 會讓使用者
看到屬於別張票的畫面，而那個畫面看起來是對的）。

```bash
PORT=<PORT>
<preflight 指令，沒有就刪掉這行>
nohup <devCommand> > <logPath> 2>&1 &
echo $! > .dev-server.pid
for i in $(seq 1 <startTimeoutSec>); do
  curl -sf "http://localhost:$PORT<readyPath>" -o /dev/null && break; sleep 1
done
open "http://localhost:$PORT<第一個要驗的路徑>"
```

**輪詢到 ready 才開，不要 sleep 固定秒數**——冷啟動慢就會開到空白頁，而空白頁會被誤讀成
「這張票做壞了」。**server 起不來就不要開頁**：`tail -30 <logPath>`，把真正的錯誤寫進
RESULT.md，並在清單開頭標「server 起不來，以下全部未驗」。硬開一個 404 比不開更糟。

**server 留著不要關**，那是使用者要驗的東西；worktree 由我來收。

接著把清單寫進 RESULT.md 的 `## 人工驗收清單` 段落。**寫法照 STE100 的精神**——
目的是讓使用者不需要猜：

- **一句一個動作**，要做兩件事就拆成兩步
- **祈使句、動詞開頭**：「點擊」「輸入」「捲動到」
- **主動語態**，一句以 20 字為度
- **同一個元件全程用同一個名稱**，不要一下「儲存鈕」一下「送出鈕」
- **禁用模糊詞**：不准出現「正常」「適當地」「應該」「檢查一下」
- **條件在前、動作在後**：「若出現『連線失敗』，點擊『重試』。」
- **預期結果必須可觀察**：寫看得見的文字、數字、狀態變化，不寫「資料有正確寫入」
- **前提（帳密、種子資料、必要開關）寫在所有步驟之前**，不要藏在括號裡
- 每一項標**對應的驗收條件**，並寫**「不符時請回報什麼」**（錯誤訊息全文、Console 紅字、截圖）
- **只列你驗不到的畫面行為**。已經被 `verify:*` 守住的邏輯不要再叫使用者點一次。
  3～6 項是健康的，超過 8 項代表自動化驗證欠太多——那就在 RESULT.md 講明
- **你自己沒驗過的項目要在標題標出來**（例如「（我完全沒驗）」），那是你欠的債，
  標出來使用者才會多看兩眼

一項長這樣：

```
### V1 新增訂單後，列表立即出現該筆（票券 AC-2）
1. 點擊右上角的「新增訂單」按鈕。
2. 在「客戶名稱」欄輸入 `測試A`。
3. 點擊「儲存」按鈕。

預期：對話框關閉。清單最上方出現一列「測試A」。
不符時請回報：畫面上的錯誤訊息全文，以及 DevTools Console 的紅色訊息。
```

在 RESULT.md 寫一行說明理由即可，不要硬湊一個 URL。>

## 完成後要做的事
1. 在 <branch> 上 commit（訊息用繁體中文，conventional commit 格式）。
2. **不要 push、不要 merge、不要碰 <base>、不要碰別的分支、不要動任何其他票。**
3. **不要改動 Linear 的票券狀態、不要動 labels、不要碰其他票** —— 那是主控 Agent 的職責。
   但**這張票的實作紀錄註解由你自己寫**：`save_comment({ issueId: "<TICKET>", body: ... })`，
   標題 `## 實作紀錄（codex pane · <TICKET>）`，格式照
   `<主 repo>/.claude/linear-workflow.md` 的「註解怎麼寫」。結論在前、證據往摺疊區沉，

   worktree 會被移除、RESULT.md 會跟著消失，這則註解才是永久紀錄。

   - 與票券描述不同的決策及理由
   - 票上沒列但你遇到並處理掉的邊界情境
   - **已知限制與未驗證部分**
   - **`## 人工驗收清單`**（見上一段的寫法與模板），以及測試頁實際開在哪個網址
   - <若有部署或營運步驟：正式環境要做什麼>

RESULT.md、.dev-server.pid、dev server 的 log 檔——它們是給我看的，不是產出。

## 逐段說明

**「自己讀票」＋「一併讀解鎖註解」** —— 讀票省你的 context，而票是唯一權威。**讀解鎖註解是分波推進的複利所在**：上一波你審碼發現的邊界、效能特性、可以照抄的實作，全都寫在那裡。實測有效——第二波的 pane 因此不必自己重新發現「回傳的是原物件本身」「`optimizedCount === 0` 的語意」「`NaN` 不被當缺座標」這三件事，而且它真的照著把 `NaN` 正規化掉了。

**主 repo 唯讀** —— 規格文件常在 gitignore 的目錄裡（vault、docs、報告），只能從主 repo 讀。但絕不能在那裡寫，否則兩個 pane 會互相踩。

**「上游已經做好的東西」** —— Codex 不知道上一張票做了什麼。不寫的話它會重新實作一份，而那份與已經進 base 的那份會有微妙差異。**特別要寫「已由整合時實測確認的事實」**，那些是你補測出來、票面沒有的資訊。

**「照既有模式做」＋指路到具體檔案** —— 這是實測中效果最明顯的一段。Codex 沒讀過你的架構決策，但**它很擅長照著讀懂的模式做**。指路到有詳盡檔頭註解的既有實作，比寫任何抽象規範都有效——實測結果是它完整鏡像了模組層級 promise 快取、失敗時清快取、刻意沒有 loading 狀態這三個設計決策，並在 RESULT.md 裡解釋了為什麼。

**同波鄰居與獨佔檔** —— pane 知道有鄰居才會自我克制。獨佔宣告要正反都寫（對 A 說「你獨佔」、對 B 說「你不要碰」），只寫一邊會有人越界。

**共用檔的衝突紀律** —— 中風險共用檔（append-only 清單、樣式表尾段、路由表）仍可同波，但要下紀律。**「不要順手重排」這句必須明寫**，否則整個檔會變成一團無法 review 的 diff。

**環境已備好、不要 npm install** —— 不寫的話它會花好幾分鐘重裝一份已經在那裡的 `node_modules`。

**閘門清單 + 排除理由** —— **這是本工作流最重要的一段。** 只列當下實際會綠的；排除的要**寫出真因**並明令不要去修。不寫理由的話它會以為那是自己弄壞的，然後花整輪去修一個與這張票無關的既有問題。

**點名關鍵閘門與當前斷言數** —— 給它一個具體的回歸判準。實測有效：pane 把斷言數從 31 加到 35 並在 RESULT.md 裡主動報告「原 31 條未減少」。

**建置輸出重導** —— 數千行的建置輸出直接進 context 會癱瘓 pane。

**補自動化驗證** —— 自動守門薄的專案值得專門要求一段。實測有效，而且這是唯一能跨波累積的資產。

**對抗式自審** —— 要具體到這張票的類型。「純演算法票」要檢查收斂條件與邊界節點數；「拆頁票」要檢查兩條路由的行為有沒有悄悄分岔；「地圖票」要檢查序號對照與 effect 依賴。抽象地說「請自我 review」沒有用。

**誠實度要求** —— **不要只說「請誠實」。** 要指出這個專案的守門具體缺在哪、`build` 綠燈的邊界在哪、以及**寫錯會害到誰**（下游票號）。實測中最好的一次結果是 pane 把驗收條件 1 直接標成「未驗證」而不是含糊的「部分通過」——那正是這段起了作用。

**不准 push / merge / 動 base / 動 Linear** —— 整合與看板正確性是主控 Agent 的職責。即使 Codex 有 Linear MCP 也要明令，否則看板上的因果關係會變得無法追溯。

**RESULT.md 不要 commit** —— 不寫的話它會 commit 進去，然後每條分支都在同一個檔案上衝突。

---

**起 server、開頁、寫 STE100 清單** —— 這段是整份指令裡唯一會產生「使用者真的看過畫面」這個事實的部分，其餘每一段都只是在讓程式碼更可能正確。三個細節不能省：**port 由主控分配**（撞 port 的錯最難察覺，因為畫面看起來是對的）、**輪詢到 ready 才開**（空白頁會被誤讀成功能壞了）、**server 起不來就不要開**（404 比不開更糟）。

清單要用 STE100 的規則寫，是因為驗收清單的失敗模式很固定：寫「確認顯示正常」，使用者不知道要看哪裡，回報就變成「怪怪的」，然後 pane 只能靠猜來補正——**一次模糊的措辭會換來兩三輪來回**。祈使句、一句一動作、可觀察的預期結果，這三條就解決掉八成。另外要求 pane **標出自己沒驗過的項目**：那些正是最可能壞的地方，不標的話使用者會用例行心態掃過去。

## 補正指令怎麼寫

pane 沒達標時**不要整段重述**，用同一個 pane 送只有差異的指令——它保留了讀過的票與跑過的建置：

```markdown
<具體問題>。<為什麼這是問題>。

請只改這一點，其餘不動，然後重跑 <相關閘門> 並更新 RESULT.md 的對應條目。
```

**同一張票補正兩次仍不達標就停下來問使用者。** 多半是票券規格本身有歧義，那是人要決定的事，繼續補正只會累積更難 review 的 diff。

**人工驗收不符時的補正指令，要帶使用者的原話，不要轉譯：**

```markdown
使用者驗 V3 時回報：「金額輸入 abc 按儲存，對話框關掉了，而且列表多出一筆空白的。」

請重現這個情境、修正，然後重跑 V3 並更新 RESULT.md 的對應條目。
server 保持開著，我會請他複驗這一項。
```

**轉譯成「表單驗證沒擋住非數字輸入」會磨掉關鍵細節**——「多出一筆空白的」說明問題不只在驗證，還在送出路徑。原話裡的每一個症狀都可能是線索。
