# grill-to-linear

一條龍：**訪談 → 規格書 → 拆票 → 建票**。

這個 skill 的價值在「拆票之前」。直接把一段模糊需求丟給模型拆票，拆出來的一定是漂亮但站不住的卡片——因為所有沒問清楚的地方都被猜掉了，而猜錯的成本要到開工才會爆出來。所以前半段刻意慢：一次一題把決策逼出來，讓拆票時每張卡片都對應到一個**已經確認過**的決定。

## 兩種呼叫

| 呼叫 | 行為 |
| --- | --- |
| 無參數 | 訪談 → 規格書 → 拆票草稿 → 使用者確認 → **實際建票** |
| 帶 `draft` | 走到拆票草稿為止，**一張票都不建**。使用者想先看拆法再決定要不要上 Linear。 |

## 階段 0：讀設定，沒有就停

讀專案根的 `.claude/linear-workflow.json`。這是 `linear-workflow-init` 產出的檔案，裡面有 `team`、`states`、`containerMode`、`apiRequireLabel`、`conventions.projects`。

**檔案不存在就停下來**，告訴使用者先跑 `/linear-workflow-init`，並說明沒有它就不知道要建到哪個 team、Blocked 欄的 state id 是多少。硬猜這些值的後果是把票建到錯的 team，或把票推進錯的狀態欄——兩者都得手動善後，而 **Linear MCP 沒有刪票工具**。

帶 `draft` 呼叫時設定檔可以缺——草稿不碰 Linear。缺了就照常往下走，只在最後提醒一句「要建票得先跑 init」。

## 階段 1：快速探索 codebase

目的**只有一個**：讓你在階段 2 問得出對的問題，而不是問一堆看程式碼就知道的事。所以這一步要短。

- 專案有 gitnexus MCP 就用它（`route_map`、`context`、`impact` 對「這個需求會碰到哪些模組」最快）；沒有就 Glob / Grep 摸相關目錄。
- 找三件事：**這個需求會碰到哪些模組**、**這些模組現有的測試 seam 在哪**、**這個區域有沒有 ADR 或既有慣例**。
- 專案的領域詞彙要抄下來。規格書與票券標題全程用專案自己的講法，不要自創同義詞——看板上兩套詞彙並存，日後查票會查不到。

**事實自己查，決策才問人。** 「目前登入用的是哪套 session 機制」是事實，去讀。「這次要不要換成 JWT」是決策，留給階段 2。

需求是全新的、專案裡還沒有對應程式碼時，這一步幾乎沒東西可探，直接進階段 2 就好。

## 階段 2：多輪訪談

用 `AskUserQuestion`，**一次一題**。

一次丟四題會拿到品質差的答案，因為使用者被迫在還沒想清楚上一題的情況下回下一題；更糟的是同一批裡的下游問題無法根據上游答案調整，常常問出一個因為前一題答案而根本不成立的問題。逐題慢，但每一題都能踩在前一題的答案上。

**開場先宣告預估題數與主軸**，例如「大概 6–8 題，會依序談範圍邊界、資料流、失敗情境、驗收」。使用者需要知道這要花多久，才決定現在要不要認真談。估完就照著走；中途發現要加題，講一聲再加。

### 每一題長什麼樣

- **2–4 個具體選項**，其中一個標 `(推薦)` 放在第一個，並在描述裡寫清楚為什麼推薦——通常是既有慣例、風險較低、或改動面積最小。使用者不確定時有東西可以靠。
- 選項要**具體到可以直接寫進規格**。「用比較穩健的做法」不是選項，「失敗時降級讀主資料庫，記一筆 warning」才是。
- UI／流程／資料結構類的題目，用 ASCII Art 或小段結構把選項畫出來放進 `preview`。文字描述兩個版面的差別，遠不如把它們並排畫出來。
- 使用者總是可以選 Other 自己寫。他寫的東西若與你的推薦衝突，**採納他的，但把你原本的顧慮講出來**再往下走——他有你沒有的背景，而你有他可能沒想到的邊界。

### 問什麼

依序走這幾條主軸，每條問到有結論再進下一條。題材與具體問法見 `references/interview-playbook.md`——需要挑題目時讀它。

1. **範圍邊界**：這次要解的到底是哪個問題？什麼明確**不做**？
2. **使用者與情境**：誰在什麼情況下用？有幾種角色／權限？
3. **資料與狀態**：資料從哪來、存哪、誰是唯一真相來源？
4. **失敗與邊界情境**：失敗了怎麼辦？空狀態、併發、離線、權限不足。
5. **既有系統整合點**：接哪些既有模組？契約由誰定？後端要不要動？
6. **驗收與可觀測性**：怎樣算做完？怎麼知道它在線上是好的？

### 什麼時候停

停止條件是**「再問下去也不會改變拆票結果」**，不是題目問完了。

每問完一題，自己回答一次：「現在拆票，還有哪張卡片的內容是我在猜的？」猜的部分就是下一題。沒有了就收手——問到使用者失去耐性，後面幾題會得到隨便選的答案，那比不問更糟，因為錯誤決策被包裝成確認過的決策寫進了規格。

使用者喊「夠了，直接拆」就立刻停，並把還沒問到的部分在規格書的「待確認」段落列出來，別默默替他決定。

**收尾要覆述。** 訪談結束、動手寫規格之前，用 5–10 條把達成的共識列出來請使用者確認。這是抓「你以為他答應了、其實他理解成別的意思」的最後一道關卡，而那種誤會在拆完票才發現要重來一輪。

## 階段 3：寫規格書

寫到 `.claude/report/${YYYY_MM_DD}/<feature-slug>-規格書.md`（日期用今天，`YYYY_MM_DD` 格式），繁體中文。模板見 `references/spec-template.md`。

- 有流程／狀態機的部分用 Mermaid 畫出來。**換行一律用 `<br/>`，不要用 `\n`**。
- 不寫具體檔案路徑與程式碼片段——它們過期得非常快，而規格書會被讀很多次。例外：訪談中確定下來的 schema、型別形狀、狀態機轉換表，這些用散文講不清楚，直接內嵌。
- 寫完告訴使用者路徑，讓他要看可以先看，但**不用等他看完**才進階段 4——拆票草稿本來就是下一輪確認的機會。

## 階段 4：拆票草稿

### 切法：垂直切片

每張票切一條**窄但完整**穿過所有層（schema → API → UI → 測試）的路徑，不是切某一層的橫剖面。判準：

- 這張票做完，能不能單獨 demo 或驗證？不能就是切錯了。
- 塞得進一個全新的 context window 嗎？塞不下就再拆。
- 要先 prefactor 的排最前面。「先讓改動變容易，再做那個容易的改動。」

**大範圍機械式重構是例外。** 改一個共用型別、改一個欄位名，這種改動的爆炸半徑橫跨整個 codebase，一次編輯就打斷上千處呼叫，切不出能單獨綠燈的垂直切片。這時改用 expand–contract 排序：先 expand（新形式與舊形式並存，什麼都不壞）→ 依爆炸半徑分批遷移呼叫端（每批一張票，都被 expand 擋著，批與批之間 CI 保持綠）→ 最後 contract（沒有呼叫端了才刪舊形式，被所有遷移票擋著）。

### 每張票要標的東西

- **標題**：用專案領域詞彙的短描述。
- **blocked by**：哪幾張票必須先完成。沒有就是「無，可立即開工」。只標**真正卡住它**的票，不要因為「照順序做比較順」就連一條邊——多餘的依賴會讓看板上一堆票假性卡死。
- **交付什麼**：這張票讓什麼行為從不能用變成能用，從使用者角度寫，不是分層的實作清單。
- **要不要後端**：這張票的阻塞如果得有人動後端（API 未提供、契約不完整、錯誤碼未定義、回傳缺欄位）才能解，標記出來——它會掛 `apiRequireLabel` 並推到 API Require 欄。
- **優先序**：對應 Linear 的 1=Urgent / 2=High / 3=Medium / 4=Low。**不確定就不要設**（留 0 = No priority），假的優先序比沒有優先序更會誤導排序。

### 拿草稿去問使用者

把整份草稿以編號清單列在對話裡（不是寫成檔案——這一輪是要來回改的），然後問三件事：

- 粒度對嗎？太粗還是太細？
- 依賴邊對嗎？每張票是不是只依賴真正卡住它的票？
- 有沒有哪幾張該合併、哪張該再拆？

改完再列一次，直到使用者說可以。**這一輪一定要跑完**，因為下一步就不可逆了。

帶 `draft` 呼叫的話，approve 之後把草稿寫進規格書同一個資料夾的 `<feature-slug>-拆票草稿.md`，然後結束。

## 階段 5：建票

到這一步之前，使用者必須已經明確 approve 過草稿。**Linear MCP 沒有刪票工具**，建錯的票只能請使用者去 Linear 手動刪（開票 → `⋯` → Delete），而且票號永久消耗不會回收。這不是可以「先建了再說」的操作。

### 5.1 決定容器歸屬

依設定檔的 `containerMode` 決定容器長什麼樣：

| 模式 | 容器 | 掛法 |
| --- | --- | --- |
| `project` | Linear Project | `save_issue({ project: "<名稱或 id>" })` |
| `parent` | 一張父議題 | `save_issue({ parentId: "<票號>" })` |

讀設定檔的 `conventions.projects`（init 探測到的既有 Project）。同時用 `list_projects` 查一次現況確認它沒過期。

用 `AskUserQuestion` 問一題，選項依現況組：

- 既有容器之中語意最接近的那個，標 `(推薦)` 排第一
- 新開一個容器當這批工作的容器
- 平鋪，不掛容器

**專案完全沒有容器、而這批票只有兩三張時，直接建議平鋪**——為三張票開一個 Project 只是多一層點擊。

選了新開 Project 就先用 `save_project` 建起來拿到 id；選了新開父議題就先建那張票。

**分階段的需求可以順帶建 Milestone**（`save_milestone`），這是 Linear 有而 Jira 沒有的東西。但別主動推銷：只有使用者在訪談中明確談到階段性交付時才提。

### 5.2 依序建票

**blockers 先建。** 只有先建好，後面那張票的依賴才有真實票號可以指。整批票依拓撲順序走（沒有 blocker 的先，然後是 blocker 都建完的，以此類推）。

每張票用 `save_issue`（**不帶 `id` 就是建立**）：

```
save_issue({
  team: "<team>",
  title: "<標題>",
  description: "<票券模板，Markdown>",
  project: "<containerMode=project 且有容器時>",
  parentId: "<containerMode=parent 且有容器時>",
  priority: <0-4>,
  blockedBy: ["PROJ-61"],          ← 上游已建好才填
  labels: ["api-require"]          ← 需要後端的才填
})
```

幾個 Linear 特有的注意事項：

- **`description` 直接寫真正的換行字元**，不要寫成 `\n` 逸出序列——會逐字保留，貼上去就是一團 `\n`。
- **`labels` 是整組取代語意。** 建票時無所謂（本來就沒有 label），但**更新既有票時一定要先 `get_issue` 讀現有清單再送併集**，否則會把別人掛的標籤清光。這是 Jira 使用者最容易帶錯過來的習慣。
- **`blockedBy` / `blocks` 是附加語意**，送出不會清掉既有關係。與 `labels` 剛好相反，兩者不要記混。
- label 名稱不存在時 Linear 會自動建立，不必先跑 `create_issue_label`。
- **立刻記下回傳的票號**，並在對話裡逐張回報。中途失敗時，使用者必須知道已經建了哪幾張——不然他重跑一次就會拿到兩套重複的票。

## 要做什麼

這張票讓什麼行為變成可用，從使用者角度寫。不要逐層列實作步驟。

## 完成的樣子

做完之後可以怎麼驗證它真的動了——可以是操作路徑、可觀察的結果，或該綠的測試。

## Blocked by

擋住這張票的票號與標題，或「無，可立即開工」。

## 來源

規格書路徑（例：`.claude/report/2026_08_09/登入流程改版-規格書.md`）。

</票券模板>

票券描述裡**不要放 Mermaid**——Linear 的議題描述不渲染它，貼上去只會是一團原始碼。流程圖留在規格書裡，票上用「來源」那行指過去。

（**Linear Document 可以放 Mermaid**。規格書若要同時放上 Linear 讓團隊看得到，用 `save_document` 建一份文件，那裡渲染得出來。這是可選的加值步驟，使用者沒要求就別做。）

同樣不要放檔案路徑與程式碼片段，例外與規格書相同（schema、型別形狀、狀態機這類用散文講不清的東西）。

### 5.3 補依賴關係

若某張票的 blocker 在它建立時還沒建好（拓撲順序理論上不該發生，但批次中途失敗重跑時會遇到），事後補：

```
save_issue({ id: "PROJ-62", blockedBy: ["PROJ-61"] })
```

`blockedBy` 是附加語意，重複送同一組不會出錯，也不會清掉既有的。這比 Jira 的 `createIssueLink` 單純——**不需要**先檢查站台有沒有 Blocks 這種 link type，Linear 的阻塞關係是內建的。

### 5.4 推狀態

有 blocker 未完成的票，照設定檔推到對應狀態，讓看板一眼看得出今天能拿哪幾張：

| 情況 | 推到 |
| --- | --- |
| 被其他票擋住 | `states.block.id` |
| 要等後端提供 API | `states.apiRequire.id`（並已掛 `apiRequireLabel`） |
| 沒有 blocker | 不動，留在建票的預設狀態 |

推狀態就一步：`save_issue({ id, state: "<state id>" })`。Linear 沒有 transition 的概念，任何狀態都能直接轉到任何狀態，**不需要**先查「這張票當下可用的轉換」。

**一律送 state id，不要送名稱或 type。** 送 `"started"` 會撞到 team 裡任何一個 `started` 型的欄（In Progress 與 In Review 都是），送名稱則會在欄位改名之後靜默對錯。

設定檔裡該狀態是 `null`（init 判定這個 team 根本沒有那一欄），**停下來問使用者**，不要挑一個看起來合理的欄推。Linear 任何狀態都能互轉，所以推錯欄一定成功、一定不報錯——這比 Jira 更危險，Jira 至少有機會被 workflow scheme 擋下來。

### 5.5 回報

用依賴順序列出建好的票，讓使用者一眼看出從哪張開工：

```
〔已建立〕Project「登入流程改版」
  PROJ-61 抽出 session 存取層              Todo         ← 可立即開工
  PROJ-62 JWT 簽發與驗證                    Blocked      ← blocked by PROJ-61
  PROJ-63 登入頁串接新 token 流程            Blocked      ← blocked by PROJ-62
  PROJ-64 舊 session 資料遷移               API Require  ← 等後端提供匯出端點

規格書：.claude/report/2026_08_09/登入流程改版-規格書.md
```

## 不要做的事

- **不要**在使用者 approve 草稿之前建任何票。這是這個 skill 唯一不可逆的動作。
- **不要**跳過訪談直接拆票。使用者若明說「不用問了直接拆」，照辦，但把你猜掉的決策在草稿裡標出來。
- **不要**用 `labels` 更新既有票而沒先讀現有清單。那會靜默清光其他標籤。
- **不要**動這批票以外的任何票。重排優先序、關重複票、改 Project 歸屬都要先問。
- **不要**執行 `git add` 或 commit。規格書要不要進版控由使用者決定。
- **不要**在建票中途失敗時默默重試整批。回報已建的票號，讓使用者決定是續建還是收拾。
