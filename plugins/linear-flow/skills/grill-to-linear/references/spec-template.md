# 規格書模板

存到 `.claude/report/${YYYY_MM_DD}/<feature-slug>-規格書.md`，繁體中文。

段落順序照下面走。內容不夠的段落可以省略整段，但**不要**留一個空標題——空標題會讓讀的人以為「確認過沒有」，而其實是「沒問到」。

---

```markdown
# <功能名稱> 規格書

> 訪談日期：YYYY-MM-DD ｜ 專案：<projectKey>

## 問題陳述

使用者現在遇到什麼問題，從使用者角度寫。不要寫成技術現況描述。

## 解決方案

要怎麼解，從使用者角度寫。一段話講得完最好。

## 使用者情境

編號列出情境，格式：

1. 身為 <角色>，我想要 <功能>，以便 <好處>

這份清單要寫得夠長夠細，涵蓋這個功能的各個面向——包含異常路徑，不是只有快樂路徑。

## 流程

有狀態轉換或多步驟流程時，用 Mermaid 畫出來。換行一律用 `<br/>`。

    ```mermaid
    flowchart TD
      A[使用者送出] --> B{驗證通過?}
      B -->|是| C[寫入並回傳]
      B -->|否| D[回錯誤<br/>保留已填欄位]
    ```

沒有流程可畫就整段省略。硬畫一張只有兩個框的圖沒有意義。

## 實作決策

訪談中定下來的決策，逐條寫，**每條附上為什麼**。理由比結論重要——半年後回頭看，看得懂當時的取捨才知道現在能不能改。

可以包含：要動哪些模組、模組介面的變化、架構決策、schema 變更、API 契約、特定互動行為。

不寫具體檔案路徑與程式碼片段——它們過期得很快。例外：schema、型別形狀、狀態機轉換表這類用散文講不清楚的，直接內嵌，並註明它是決策的一部分。

## 測試決策

- 好的測試長什麼樣（只測外部行為，不測實作細節）
- 哪些模組要測
- 既有的類似測試可以參考哪些（prior art）

## 不做的事

明確排除的範圍。這一段的價值在於**擋住後續的範圍膨脹**——寫得越具體越擋得住。

## 待確認

訪談中沒問到、或使用者喊停時還懸著的決策。逐條寫清楚**卡在什麼地方、誰能決定**。

沒有懸而未決的事就整段省略。有的話絕對不能省——把猜測寫成定案是這份文件最糟的失敗方式。

## 其他備註

其他值得記下來的事。
```
