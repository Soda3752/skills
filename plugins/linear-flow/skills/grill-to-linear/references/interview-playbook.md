# 訪談題庫

六條主軸的題材與問法。**不要照單全問**——這是挑題目用的，一輪訪談通常只會用到其中 6–10 題。

挑題原則：問那些**答案不同會導致拆票結果不同**的。答案不影響拆票的問題，再有趣都跳過。

每一題都要附 2–4 個具體選項，第一個標 `(推薦)`。選項要具體到可以直接抄進規格書。

---

## 1. 範圍邊界

先問這條，因為它決定後面五條要問多深。範圍收窄一次，可以省掉三四題。

- 這次要解的核心問題是哪一個？（如果使用者一口氣講了三個痛點，請他排優先序——通常只有第一個該進這輪）
- 什麼明確**不做**？（out of scope 寫得越清楚，拆票越不會膨脹）
- 這是一次到位，還是先做能動的版本再迭代？
- 有沒有時間點壓著？（demo、發版、對外承諾）時間壓力會直接改變切片粒度
- 現有行為要保留嗎，還是取代掉？舊路徑要留多久？

<好的選項範例>
Q：舊的密碼登入要保留嗎？
[1] 保留，兩種並存，舊帳號不受影響 (推薦)——改動面積最小，不需要資料遷移票
[2] 保留但標記 deprecated，三個月後移除——多一張排程移除票
[3] 直接取代，所有帳號強制重設密碼——多一張遷移票 + 一張通知信票
</好的選項範例>

## 2. 使用者與情境

- 誰在用？有幾種角色？不同角色看到的東西一樣嗎？
- 在什麼情境下觸發？（主動操作／背景排程／被別的流程呼叫）
- 使用頻率量級？（一天十次 vs 一秒十次，會導致完全不同的技術決策）
- 第一次使用與第一百次使用的體驗要不要不同？（引導、空狀態）

角色數量直接影響票數：三種角色權限不同，很可能就是三張票而不是一張。

## 3. 資料與狀態

- 資料從哪來？誰是唯一真相來源？
- 存在哪？要不要持久化，還是活在記憶體／快取就好？
- 要新欄位或新表嗎？既有資料怎麼辦（有預設值嗎、要不要 backfill）？
- 誰可以改它？改了之後其他地方要跟著更新嗎？
- 有沒有並行寫入的可能？兩個人同時改怎麼辦？

schema 變更幾乎一定自成一張票，而且是所有票的 blocker——所以這條要問清楚，它決定了依賴圖的根。

## 4. 失敗與邊界情境

這條最容易被跳過，也最容易在開工後炸出來變成計畫外的票。

- 依賴的東西掛掉時怎麼辦？（降級／回錯誤／重試／用舊資料）
- 空狀態長什麼樣？（沒有資料、第一次來、全部被篩掉）
- 權限不足時是隱藏、鎖住、還是給錯誤訊息？
- 網路慢或斷線時？要不要離線可用？
- 超量怎麼辦？（分頁、上限、節流）
- 部分成功怎麼辦？（三筆成功兩筆失敗，要不要整批回滾）

<好的選項範例>
Q：快取失效時怎麼處理？
[1] 降級讀主資料庫，記 warning (推薦)——使用者無感，維運看得到
[2] 直接回錯誤讓前端 retry——實作最簡單，但尖峰時體驗差
[3] 回傳上一次的快照並標記為過期資料——要多一張快照儲存的票
</好的選項範例>

## 5. 既有系統整合點

- 會碰到哪些既有模組？（階段 1 探索到的結果拿來對答案，別當問題問）
- 後端要不要動？契約由誰定、什麼時候能拿到？
- 有現成的測試 seam 可用嗎，還是要開新的？（新 seam 越少越好，能用既有的就用既有的）
- 有沒有 ADR 或既有慣例限制做法？
- 第三方服務？失敗率與 SLA 知道嗎？

「後端要不要動」的答案是 yes 的部分，會變成掛 `api-require` label 的票——所以要問到具體是**哪一段**需要後端，而不是籠統的「有些地方要」。

## 6. 驗收與可觀測性

- 怎樣算做完？（能講出一條可以走一遍的路徑最好）
- 要不要寫測試？測哪一層？
- 上線後怎麼知道它是好的？（log、指標、報表）
- 出問題怎麼發現？誰會先知道？
- 要不要 feature flag／灰度？

驗收條件講不出來的票，通常是切得太模糊——這種訊號比答案本身更有價值，抓到就回頭把那張票再拆一次。

## 收尾覆述

訪談結束後，用 5–10 條列出共識請使用者確認。格式：

```
〔目前的共識〕
1. 這輪只做 X，Y 與 Z 明確不做
2. 舊路徑保留並存，不做資料遷移
3. 快取失效降級讀主資料庫
...
以上對嗎？有沒有哪條跟你想的不一樣？
```

覆述抓的是「你以為他答應了、其實他理解成別的意思」。這種誤會若留到拆完票才發現，整輪得重來。
