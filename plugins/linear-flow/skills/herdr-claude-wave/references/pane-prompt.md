每一段都對應一個實際踩過的坑。**照結構組，但內容要換成這個專案、這張票的真實情況**——模板裡的具體檔名與理由是範例，照抄過去會變成謊話。

## 為什麼是散文而不是 slash command

Claude pane 認得 skill，所以理論上可以像 `parallel-loop` 那樣只送一行 `/some-ticket-skill PROJ-111`。**分波推進的場景不適合走那條路**，兩個理由：

1. **一波裡每張票的脈絡差很多**——閘門清單、鄰居是誰、獨佔哪些檔、指路到哪個既有實作，全都是逐票不同的。slash command 傳不進去這些，最後還是得補一段散文，變成維護兩份。
2. **`parallel-loop` 走 slash command 是因為它的任務書有 200 行且完全通用**（每票只差票號與 port）。本 skill 沒有那份通用任務書。

散文加標題的效果好，因為理由講得出來——而理由是 pane 自己判斷邊界情境時唯一能依據的東西。**指令裡每一條限制都附上「為什麼」。**

送出方式用 `"$(cat 檔案)"`，不要把內容 inline 展開在指令行裡：

```bash
herdr agent prompt proj-111 "$(cat /tmp/proj-111-prompt.md)"
```

雙引號包住的 `$(cat …)` 不會對檔案內容做二次展開，反引號、`$(...)`、中文、路徑插值都安全。**inline 展開才會被 shell 靜默吃掉一段，然後 pane 收到殘缺的指令照做。**

## 完整模板

```markdown
你在 git worktree <worktree 絕對路徑> 裡，分支 <branch>，從 <base>@<hash> 建立。
請把 Linear 票 <TICKET> 做到可以合併為止。

## 第一步：自己讀票
用 Linear MCP 執行 get_issue({ id: "<TICKET>", includeRelations: true }) 讀完整描述與驗收條件。
**這張票上有一則我剛寫的「已解鎖」註解，用 list_comments({ issueId: "<TICKET>" }) 一併讀** ——
裡面寫了現在可以直接用什麼、以及該避開的坑。票與註解是唯一權威，
不要靠我這則訊息裡的摘要做事。

## 你可以讀但絕對不能寫的地方
主 repo <主 repo 絕對路徑> 我用 --add-dir 開給你了，**但它只能讀**
（規格文件 <實際路徑> 在那裡，那個目錄在 gitignore 裡，worktree 帶不過來）。
你有寫入那裡的能力，但同一波還有別的 pane 在跑，往主 repo 寫會互相踩，
而且那些改動不在任何一條分支上，我整合時看不到。
**任何寫入動作只能發生在你自己的 worktree 內。**

## 環境已經幫你備好，不要重做
node_modules、<gitignore 的設定檔清單>、.claude/、CLAUDE.md 都已經複製到你的 worktree。
**不要跑 npm install / npm ci。**
worktree 裡的 .claude/ 是主 repo 的複本，**你只讀它，不要在裡面寫任何東西** ——
你唯一的產出檔是 worktree 根目錄的 RESULT.md。

## 上游已經做好的東西，直接用，不要重寫
<具體匯出／元件／路由，附檔案路徑>
<已由整合時實測確認的事實，例如「66 家店只要 15 ms，可以放心做成同步呼叫」>
<可以照抄的既有實作：「X 已經做過一次完整流程，包含 A、B、C。照著做，不要重新發明。」>

## 照既有模式做，不要另發明一套
專案已經有 <同類實作> 走完全相同的路徑（<票號>建立），
**先把這幾個檔讀完再動手，然後鏡像它**：
- <檔案 1> — <裡面有什麼、檔頭註解交代了什麼設計理由>
- <檔案 2> — <同上>
這些理由對你這張票同樣成立，照做。

## 這一波還有誰在跑
同時有另一個 Claude pane 在做 <TICKET-B>（<標題>），它的戰場是 <檔案清單>。
**這些檔你一個都不要碰。**
<獨佔檔宣告：「package.json 這一波由你獨佔」或「你不要碰 package.json」>

**唯一的共用檔是 <路徑>，兩邊都會往檔尾追加。衝突紀律：**
- 新內容一律加在**檔案最末端**，並用註解標出區塊（例如 `/* <TICKET> <用途> */`）
- **只改最小必要行數，絕對不要順手重排、合併或重構這個檔的既有內容**
- 不要動 <前一張票> 在尾段加的那批內容

## 驗證閘門（只跑這 N 條）
<逐條列出當下實際會綠的指令>

**刻意排除的 M 條與理由（不要去修，那不是你的票）：**
- <指令> — <真因，例如「輸入檔 X 在 base 分支上就已經不存在，動工前就是紅的」>
- <指令> — <真因，例如「需要 dev server 在跑，沒起 server 就是 404，動工前就是紅的」>

<若某條閘門對這張票特別重要就點名>
**`<指令>` 對你特別重要**（目前 N 條斷言），它正是涵蓋 <範圍> 的那一支。
若你的改動讓它的斷言數變少或行為改變，那是回歸，要停下來查清楚。

建置輸出動輒數千行：一律重導到檔案再看結尾，例如
  npm run build > /tmp/<ticket>-build.log 2>&1; tail -30 /tmp/<ticket>-build.log
不要讓完整輸出直接進你的 context。

## 補自動化驗證
如果你的邏輯有任何可以用純函式驗證的部分，優先加進既有的 <腳本> 或新增一支 `verify:*` 腳本
—— 這是這個專案唯一有效的自動守門，比在 RESULT.md 裡宣稱「應該沒問題」有價值得多。

## 你自己要做的對抗式自審（用舉證，不要用感覺）
程式寫完、閘門全綠之後，回頭讀一次自己寫的碼。
**不要問「這寫得好嗎」——那個問題你一定回答得出漂亮的答案。**
改成逐項回答：「**給我一組會讓這段壞掉的輸入。**」舉不出來才算過，
舉得出來就去修，並把那組輸入補成測試。

特別檢查：
- <這類型的票最容易出錯的 3~4 點，具體到這張票>

<地基票／演算法票／安全相關的票加這一段>
做完自審之後，**另外跑一輪 codex review 當作異質意見**：
  codex exec "請閱讀 <檔案清單> 的改動並嘗試證明它是錯的。不要客氣。"
把它提出的每一點在 RESULT.md 裡回應（接受／反駁＋理由）。

## 誠實度要求（這一點最重要）
<專案的實際守門缺口，例如「本專案 E2E 已關閉，瀏覽器層完全沒有任何自動守門」>
`typecheck` / `lint` / `build` 全綠**完全不代表 <實際要驗的東西>**。
你沒有 <實際驗證動作> 就必須標成「未驗證」。

我要提醒你一件結構性的事：**收你這張票的是另一個 Claude，跟你同一個模型。**
你覺得對的地方，它多半也會覺得對 —— 所以你的「我判斷這樣沒問題」在我這裡幾乎沒有證據力。
有證據力的只有兩種：**你實際跑出來的輸出**，或**Codex 那種異質來源的背書**。
兩者都沒有就標「未驗證」，那不丟臉，把沒驗的寫成通過才會害到後面接手 <下游票號> 的人。

## RESULT.md 邊做邊寫，不要最後才回想
你的 context 會 auto-compact，做到後面就想不起前面的細節了。
**每完成一個驗收條目就立刻把該條的結論與證據追加進 RESULT.md**，不要等全部做完才寫。

## 完成後要做的事
1. 在 <branch> 上 commit（訊息用繁體中文，conventional commit 格式）。
2. **不要 push、不要 merge、不要碰 <base>、不要碰別的分支、不要動任何其他票。**
3. **不要改動 Linear 的票券狀態，也不要在票上留言** —— 那是主控 Agent 的職責。
4. 把結果寫成 RESULT.md 放在 worktree 根目錄（**不要 commit**），繁體中文，包含：
   - commit hash
   - 改了哪些檔案、為什麼
   - **驗收條件逐條對照**：每條寫「通過／部分通過／未驗證」，並附上你實際跑的驗證證據
     （指令 + 實際輸出摘要 + 斷言數，不是「我檢查過了」）
   - 與票券描述不同的決策及理由
   - 票上沒列但你遇到並處理掉的邊界情境
   - **已知限制與未驗證部分**
   - <若有跑 codex review：它提了什麼、你怎麼回應>
   - <若有部署或營運步驟：正式環境要做什麼>

## 禁止修改的檔案
<專案的 protectedPaths> + <同波其他票的戰場> + 主 repo 的一切

做完就停下來，我會來收。
```

## 逐段說明

**「自己讀票」＋「一併讀解鎖註解」** —— 讀票省你的 context，而票是唯一權威。**讀解鎖註解是分波推進的複利所在**：上一波你審碼發現的邊界、效能特性、可以照抄的實作，全都寫在那裡。

**主 repo 唯讀，而且要講出為什麼** —— 這一段在 Claude pane 版比 Codex 版更重要。Codex 版是「你沒有那個能力」，本版是「**我剛給了你那個能力（`--add-dir`），但請你別用**」。只寫「不能寫」而不寫理由的話，pane 遇到「規格文件有錯字」這種情境會覺得順手修一下是好事。

**環境已備好 + `.claude/` 只讀不寫** —— 不寫的話它會花好幾分鐘重裝一份已經在那裡的 `node_modules`。`.claude/` 那句是本版特有：worktree 裡那份是複本，pane 在裡面寫報告或改設定，主 repo 完全不會知道，而 worktree 一刪就沒了。

**「上游已經做好的東西」** —— pane 不知道上一張票做了什麼。不寫的話它會重新實作一份，而那份與已經進 base 的那份會有微妙差異。**特別要寫「已由整合時實測確認的事實」**，那些是你補測出來、票面沒有的資訊。

**「照既有模式做」＋指路到具體檔案** —— 效果最明顯的一段。指路到有詳盡檔頭註解的既有實作，比寫任何抽象規範都有效。

**同波鄰居與獨佔檔** —— pane 知道有鄰居才會自我克制。獨佔宣告要正反都寫（對 A 說「你獨佔」、對 B 說「你不要碰」），只寫一邊會有人越界。

**共用檔的衝突紀律** —— 中風險共用檔（append-only 清單、樣式表尾段、路由表）仍可同波，但要下紀律。**「不要順手重排」這句必須明寫**，否則整個檔會變成一團無法 review 的 diff。

**閘門清單 + 排除理由** —— **這是本工作流最重要的一段。** 只列當下實際會綠的；排除的要**寫出真因**並明令不要去修。不寫理由的話它會以為那是自己弄壞的，然後花整輪去修一個與這張票無關的既有問題。

**點名關鍵閘門與當前斷言數** —— 給它一個具體的回歸判準。

**建置輸出重導** —— 數千行的建置輸出直接進 context 會癱瘓 pane。

**對抗式自審用「舉證」而不是「評價」** —— 本版與 Codex 版最實質的差異。「請自我 review」對同模型幾乎無效，因為它會用寫的時候那套判準再審一次，結論當然一樣。**換成「給我一組會讓它壞掉的輸入」，問題就從評價變成舉證**——舉不出來至少是個弱訊號，舉得出來就是實打實的 bug。地基票再加一輪 codex 當異質來源。

**誠實度要求要點名「收你的人跟你同一個模型」** —— 這是本版獨有的一段，而且實質上改變了 pane 的行為誘因。Codex 版說的是「寫錯會害到下游」；本版要多說一層：**你的主觀判斷在我這裡沒有證據力，因為我跟你同一個分布**。把「未驗證」正常化，它才會誠實標。

**RESULT.md 邊做邊寫** —— Claude pane 會 auto-compact。等做完才回想的 RESULT.md，細節會失真成「應該有跑過」。

**不准 push / merge / 動 base / 動 Linear** —— 整合與看板正確性是主控 Agent 的職責。即使 pane 有 Linear MCP 也要明令，否則看板上的因果關係會變得無法追溯。

**RESULT.md 不要 commit** —— 不寫的話它會 commit 進去，然後每條分支都在同一個檔案上衝突。

## 補正指令怎麼寫

pane 沒達標時**不要整段重述**，用同一個 pane 送只有差異的指令——它保留了讀過的票與跑過的建置：

```markdown
<具體問題>。<為什麼這是問題>。

請只改這一點，其餘不動，然後重跑 <相關閘門> 並更新 RESULT.md 的對應條目。
```

**驗收條目被標成「通過」但沒有執行證據時，補正指令要問證據不要問結論：**

```markdown
RESULT.md 的驗收條件 <N> 標了通過，但沒有附實際輸出。
請把你當時跑的指令與輸出貼進 RESULT.md；如果其實沒跑過，就改標「未驗證」——
改標不會有任何後果，標錯才會。
```

**同一張票補正兩次仍不達標就停下來問使用者。** 多半是票券規格本身有歧義，那是人要決定的事，繼續補正只會累積更難 review 的 diff。
