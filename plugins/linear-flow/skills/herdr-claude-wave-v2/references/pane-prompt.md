## 為什麼是散文而不是 slash command

Claude pane 認得 skill，所以理論上可以像 `parallel-loop` 那樣只送一行 `/some-ticket-skill PROJ-111`。**分波推進的場景不適合走那條路**，兩個理由：

1. **一波裡每張票的脈絡差很多**——閘門清單、鄰居是誰、獨佔哪些檔、指路到哪個既有實作，全都是逐票不同的。slash command 傳不進去這些，最後還是得補一段散文，變成維護兩份。
2. **`parallel-loop` 走 slash command 是因為它的任務書有 200 行且完全通用**（每票只差票號與 port）。本 skill 沒有那份通用任務書。

散文加標題的效果好，因為理由講得出來——而理由是 pane 自己判斷邊界情境時唯一能依據的東西。**指令裡每一條限制都附上「為什麼」。**

送出方式用 `"$(cat 檔案)"`，不要把內容 inline 展開在指令行裡：

```bash
herdr agent prompt proj-111 "$(cat /tmp/proj-111-prompt.md)"
```

雙引號包住的 `$(cat …)` 不會對檔案內容做二次展開，反引號、`$(...)`、中文、路徑插值都安全。**inline 展開才會被 shell 靜默吃掉一段，然後 pane 收到殘缺的指令照做。**

## 做完之後：起本地服務、開測試頁、寫人工驗收清單
閘門全綠、commit 完成之後，**在使用者面前把畫面打開**。本專案瀏覽器層沒有任何自動守門，
你寫的清單是這張票唯一的視覺驗證來源。

你被分配到的 port 是 <PORT>，**只准用這個**（同一波還有別的 pane，撞 port 會讓使用者
看到屬於別張票的畫面，而那個畫面看起來是對的）。

```bash
PORT=<PORT>
<preflight 指令，沒有就刪掉這行>
nohup <devCommand> > <logPath> 2>&1 &
echo $! > .dev-server.pid
for i in $(seq 1 <startTimeoutSec>); do
  curl -sf "http://localhost:$PORT<readyPath>" -o /dev/null && break; sleep 1
done
open "http://localhost:$PORT<第一個要驗的路徑>"
```

**輪詢到 ready 才開，不要 sleep 固定秒數**——冷啟動慢就會開到空白頁，而空白頁會被誤讀成
「這張票做壞了」。**server 起不來就不要開頁**：`tail -30 <logPath>`，把真正的錯誤寫進
RESULT.md，並在清單開頭標「server 起不來，以下全部未驗」。硬開一個 404 比不開更糟。

**server 留著不要關**，那是使用者要驗的東西；worktree 由我來收。

接著把清單寫進 RESULT.md 的 `## 人工驗收清單` 段落。**寫法照 STE100 的精神**——
目的是讓使用者不需要猜：

- **一句一個動作**，要做兩件事就拆成兩步
- **祈使句、動詞開頭**：「點擊」「輸入」「捲動到」
- **主動語態**，一句以 20 字為度
- **同一個元件全程用同一個名稱**，不要一下「儲存鈕」一下「送出鈕」
- **禁用模糊詞**：不准出現「正常」「適當地」「應該」「檢查一下」
- **條件在前、動作在後**：「若出現『連線失敗』，點擊『重試』。」
- **預期結果必須可觀察**：寫看得見的文字、數字、狀態變化，不寫「資料有正確寫入」
- **前提（帳密、種子資料、必要開關）寫在所有步驟之前**，不要藏在括號裡
- 每一項標**對應的驗收條件**，並寫**「不符時請回報什麼」**（錯誤訊息全文、Console 紅字、截圖）
- **只列你驗不到的畫面行為**。已經被 `verify:*` 守住的邏輯不要再叫使用者點一次。
  3～6 項是健康的，超過 8 項代表自動化驗證欠太多——那就在 RESULT.md 講明
- **你自己沒驗過的項目要在標題標出來**（例如「（我完全沒驗）」），那是你欠的債，
  標出來使用者才會多看兩眼

一項長這樣：

## 逐段說明

**pane 自己寫實作紀錄註解，狀態仍歸主控** —— 這條在早期版本是反的（禁止 pane 留言、由主控轉述），實跑之後改掉了。原因是 worktree 一移除，`RESULT.md` 就永久消失，而主控的轉述必然流失第一人稱的判斷過程——尤其是「考慮過但沒選」那一段，轉述時最容易被當成無關細節砍掉，偏偏它是下一個接手的人最需要的。

分野是**留言權與狀態權分開**：pane 寫註解，主控寫狀態。當初禁止留言是為了保住看板因果的可追溯性，但那個顧慮真正指向的是狀態；註解只要標題標明作者，追溯性反而比單一則轉述更好。

**「自己讀票」＋「一併讀解鎖註解」** —— 讀票省你的 context，而票是唯一權威。**讀解鎖註解是分波推進的複利所在**：上一波你審碼發現的邊界、效能特性、可以照抄的實作，全都寫在那裡。

**主 repo 唯讀，而且要講出為什麼** —— 這一段在 Claude pane 版比 Codex 版更重要。Codex 版是「你沒有那個能力」，本版是「**我剛給了你那個能力（`--add-dir`），但請你別用**」。只寫「不能寫」而不寫理由的話，pane 遇到「規格文件有錯字」這種情境會覺得順手修一下是好事。

**環境已備好 + `.claude/` 只讀不寫** —— 不寫的話它會花好幾分鐘重裝一份已經在那裡的 `node_modules`。`.claude/` 那句是本版特有：worktree 裡那份是複本，pane 在裡面寫報告或改設定，主 repo 完全不會知道，而 worktree 一刪就沒了。

**「上游已經做好的東西」** —— pane 不知道上一張票做了什麼。不寫的話它會重新實作一份，而那份與已經進 base 的那份會有微妙差異。**特別要寫「已由整合時實測確認的事實」**，那些是你補測出來、票面沒有的資訊。

**「照既有模式做」＋指路到具體檔案** —— 效果最明顯的一段。指路到有詳盡檔頭註解的既有實作，比寫任何抽象規範都有效。

**同波鄰居與獨佔檔** —— pane 知道有鄰居才會自我克制。獨佔宣告要正反都寫（對 A 說「你獨佔」、對 B 說「你不要碰」），只寫一邊會有人越界。

**共用檔的衝突紀律** —— 中風險共用檔（append-only 清單、樣式表尾段、路由表）仍可同波，但要下紀律。**「不要順手重排」這句必須明寫**，否則整個檔會變成一團無法 review 的 diff。

**閘門清單 + 排除理由** —— **這是本工作流最重要的一段。** 只列當下實際會綠的；排除的要**寫出真因**並明令不要去修。不寫理由的話它會以為那是自己弄壞的，然後花整輪去修一個與這張票無關的既有問題。

**點名關鍵閘門與當前斷言數** —— 給它一個具體的回歸判準。

**建置輸出重導** —— 數千行的建置輸出直接進 context 會癱瘓 pane。

**對抗式自審用「舉證」而不是「評價」** —— 本版與 Codex 版最實質的差異。「請自我 review」對同模型幾乎無效，因為它會用寫的時候那套判準再審一次，結論當然一樣。**換成「給我一組會讓它壞掉的輸入」，問題就從評價變成舉證**——舉不出來至少是個弱訊號，舉得出來就是實打實的 bug。地基票再加一輪 codex 當異質來源。

**誠實度要求要點名「收你的人跟你同一個模型」** —— 這是本版獨有的一段，而且實質上改變了 pane 的行為誘因。Codex 版說的是「寫錯會害到下游」；本版要多說一層：**你的主觀判斷在我這裡沒有證據力，因為我跟你同一個分布**。把「未驗證」正常化，它才會誠實標。

**RESULT.md 邊做邊寫** —— Claude pane 會 auto-compact。等做完才回想的 RESULT.md，細節會失真成「應該有跑過」。

**起 server、開頁、寫 STE100 清單** —— 這段是整份指令裡唯一會產生「使用者真的看過畫面」這個事實的部分，其餘每一段都只是在讓程式碼更可能正確。三個細節不能省：**port 由主控分配**（撞 port 的錯最難察覺，因為畫面看起來是對的）、**輪詢到 ready 才開**（空白頁會被誤讀成功能壞了）、**server 起不來就不要開**（404 比不開更糟）。

清單要用 STE100 的規則寫，是因為驗收清單的失敗模式很固定：寫「確認顯示正常」，使用者不知道要看哪裡，回報就變成「怪怪的」，然後 pane 只能靠猜來補正——**一次模糊的措辭會換來兩三輪來回**。祈使句、一句一動作、可觀察的預期結果，這三條就解決掉八成。另外要求 pane **標出自己沒驗過的項目**：那些正是最可能壞的地方，不標的話使用者會用例行心態掃過去。

**不准 push / merge / 動 base / 動 Linear** —— 整合與看板正確性是主控 Agent 的職責。即使 pane 有 Linear MCP 也要明令，否則看板上的因果關係會變得無法追溯。

**RESULT.md 不要 commit** —— 不寫的話它會 commit 進去，然後每條分支都在同一個檔案上衝突。

## 補正指令怎麼寫

pane 沒達標時**不要整段重述**，用同一個 pane 送只有差異的指令——它保留了讀過的票與跑過的建置：

```markdown
<具體問題>。<為什麼這是問題>。

請只改這一點，其餘不動，然後重跑 <相關閘門> 並更新 RESULT.md 的對應條目。
```

**驗收條目被標成「通過」但沒有執行證據時，補正指令要問證據不要問結論：**

```markdown
RESULT.md 的驗收條件 <N> 標了通過，但沒有附實際輸出。
請把你當時跑的指令與輸出貼進 RESULT.md；如果其實沒跑過，就改標「未驗證」——
改標不會有任何後果，標錯才會。
```

**同一張票補正兩次仍不達標就停下來問使用者。** 多半是票券規格本身有歧義，那是人要決定的事，繼續補正只會累積更難 review 的 diff。

**人工驗收不符時的補正指令，要帶使用者的原話，不要轉譯：**

```markdown
使用者驗 V3 時回報：「金額輸入 abc 按儲存，對話框關掉了，而且列表多出一筆空白的。」

請重現這個情境、修正，然後重跑 V3 並更新 RESULT.md 的對應條目。
server 保持開著，我會請他複驗這一項。
```

**轉譯成「表單驗證沒擋住非數字輸入」會磨掉關鍵細節**——「多出一筆空白的」說明問題不只在驗證，還在送出路徑。原話裡的每一個症狀都可能是線索。
