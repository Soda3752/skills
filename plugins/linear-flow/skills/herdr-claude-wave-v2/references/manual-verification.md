# 完工開頁與人工驗收清單

**這一段解決的問題**：`typecheck` / `lint` / `build` 全綠不代表畫面對。pane 做完之後，唯一能確認「使用者看到的東西是對的」的人是使用者本人——但前提是他知道要開哪個網址、點哪裡、看到什麼才算過。**pane 完工就把測試頁開在他面前、並附上一份照著做就能驗完的清單**，把「驗收」從一件要重新載入脈絡的苦差事，變成三分鐘就能做完的動作。

`herdr-claude-wave` 與 `herdr-codex-wave` 共用本檔，差異只在誰下指令（見文末）。

## 時機與責任分界

```
pane 完工 ──▶ 起 dev server ──▶ 等 ready ──▶ open URL ──▶ 寫清單進 RESULT.md
                                                              │
主控 wait 返回 ──▶ 讀 RESULT.md ──▶ 對話裡列出清單 ──▶ 使用者驗
                                                              │
                                          ┌───────────────────┴─────────────┐
                                        驗過                            回報問題
                                          │                                 │
                            審碼 → 合併 → 整合註解收錄清單        herdr agent prompt 補正
```

| 誰 | 做什麼 | 為什麼是他 |
| --- | --- | --- |
| pane | 起 server、開頁、寫清單 | 它剛改完，最清楚哪幾個畫面行為是它動到的、哪些是它沒驗過的 |
| 主控 | 把清單搬進對話、驗收後收錄進整合註解 | 使用者只跟主控對話；pane 的畫面他不見得在看 |
| 使用者 | 照清單驗，回報不符項 | 瀏覽器層沒有任何自動守門，這是唯一的驗證來源 |

**清單是 pane 寫的、主控轉述的、使用者驗的。** 主控不要自己重寫一份——它沒改過那些碼，寫出來的會是通則而不是這張票的具體行為。

## 設定：manualVerification 區塊

放在專案的 `.claude/linear-workflow.json`，與 `parallelWave` / `goalLoop` 平行共存。**不要開獨立設定檔。**

```json
{
  "manualVerification": {
    "devCommand": "npm run dev -- --port ${PORT}",
    "baseUrl": "http://localhost:${PORT}",
    "portBase": 5173,
    "readyPath": "/",
    "startTimeoutSec": 90,
    "logPath": "/tmp/${TICKET}-dev.log",
    "routeHints": {
      "訂單列表": "/orders",
      "設定頁": "/settings"
    },
    "preflight": ["npm run db:seed"],
    "loginHint": "用 dev@example.com / dev1234 登入，種子資料已含 3 筆訂單"
  }
}
```

| 欄位 | 用途 | 缺漏時 |
| --- | --- | --- |
| `devCommand` | 起本地服務的指令，`${PORT}` 會被代換 | 從 `package.json` 的 `dev` / `start` script、`Makefile`、`docker-compose.yml` 推斷，**推斷完用 AskUserQuestion 確認一次** |
| `baseUrl` | 開頁網址樣板 | 預設 `http://localhost:${PORT}` |
| `portBase` | 一波多票時的起始 port | 讀 `devCommand` 或框架預設（Vite 5173、Next 3000、Django 8000） |
| `readyPath` | 輪詢哪個路徑判斷 server 起來了 | `/` |
| `startTimeoutSec` | 等多久還沒 ready 就算失敗 | 90 |
| `logPath` | server 輸出丟哪 | `/tmp/${TICKET}-dev.log` |
| `routeHints` | 功能名稱 → 路徑，讓 pane 寫得出精確網址 | pane 自己從路由檔推；推不出來就在清單裡寫「從首頁點『X』進入」 |
| `preflight` | 開頁前要先跑的準備（種資料、migration） | 沒有就略過 |
| `loginHint` | 測試帳密與種子資料現況 | 沒有就略過；有登入牆卻沒寫，使用者會卡在第一步 |

**缺漏不要停工。** 順序是：能從 repo 推斷的就推斷 → 猜錯代價高的（`devCommand`、`preflight`）併進第 1 步那次 AskUserQuestion 一起問 → 收工時提議把整個區塊回寫設定檔，下次免問。

**專案根本沒有可開的頁面時**（純 CLI、純 library、純 worker），這整段不適用。此時 pane 改成在 RESULT.md 寫一行「本票無可開啟的畫面，理由：<型態>」，主控在收工回報照實說，**不要硬湊一個 URL 出來**。

## port 分配與 server 生命週期

**一波多票 = 多個 server 同時活著，port 必須由主控分配，不能讓 pane 自己挑。** 兩個 pane 同挑 5173，第二個要嘛起不來、要嘛靜默搶走第一個的頁面，而使用者看到的畫面會屬於錯的那張票——這種錯最難察覺，因為畫面「看起來是對的」。

分配規則：`portBase + 波內序號`（第一張票 5173、第二張 5174⋯）。**分配結果寫進派工指令，並且要求 pane 在清單的每個網址裡都用這個 port。**

生命週期：

| 階段 | 誰 | 動作 |
| --- | --- | --- |
| pane 完工前 | pane | 背景起 server，PID 寫進 `<worktree>/.dev-server.pid` |
| 完工到驗收之間 | 無人 | **server 保持存活**——這是使用者要驗的東西 |
| 使用者驗完、審碼合併後 | 主控 | `kill $(cat <worktree>/.dev-server.pid)`，再 `git worktree remove`、`herdr workspace close` |

**`git worktree remove` 必須排在使用者回報驗收結果之後。** worktree 一刪，server 的 cwd 就消失、頁面立刻壞掉。SKILL.md 第 5 步那句「合併完立刻 remove」對這條路徑要讓位：**合併可以立刻做，remove 要等驗收回覆**。使用者一直沒回，就把 worktree 留著並在收工回報講明「PROJ-111 的 worktree 與 :5174 還開著，等你驗完再說一聲我來收」。

`.dev-server.pid` 與 log 檔一律不 commit，跟 `RESULT.md` 同樣待遇。

## pane 該執行的開頁動作

寫進派工指令，pane 照做：

```bash
PORT=<主控分配的 port>
# 1. 準備（有 preflight 才跑）
<preflight 指令>
# 2. 背景起 server，輸出進 log，PID 留檔
nohup <devCommand> > "<logPath>" 2>&1 &
echo $! > .dev-server.pid
# 3. 輪詢到真的 ready 才開頁（不要 sleep 固定秒數就開）
for i in $(seq 1 <startTimeoutSec>); do
  curl -sf "http://localhost:$PORT<readyPath>" -o /dev/null && break
  sleep 1
done
# 4. 開在使用者的預設瀏覽器
open "http://localhost:$PORT<第一個要驗的路徑>"
```

**輪詢而不是固定 `sleep`**：dev server 冷啟動時間差異極大（有沒有快取、要不要跑 migration），固定秒數要嘛白等、要嘛開到一個還沒起來的空白頁——而空白頁會被誤讀成「這張票做壞了」。

**`open` 要直接開到第一個要驗的路徑，不是首頁。** 讓使用者從首頁自己找路，等於把清單的第一步浪費在導航上。

**server 起不來就不要開頁。** `tail -30 <logPath>` 把真正的錯誤寫進 RESULT.md 的「未驗證」段，並在清單開頭標「server 起不來，以下全部未驗」。硬開一個 404 頁面比不開更糟，使用者會以為是功能壞了。

## 清單怎麼寫：STE100 精神

ASD-STE100（Simplified Technical English）的核心不是英文，是**「讓看的人不需要猜」**。這幾條規則直接套在繁體中文的驗收步驟上：

| 規則 | 怎麼做 | ✗ 反例 | ✓ 正例 |
| --- | --- | --- | --- |
| **一句一個動作** | 一個步驟只做一件事，要做兩件就拆成兩步 | 「登入後進入訂單頁並新增一筆訂單」 | 「3. 點擊『訂單』分頁。<br>4. 點擊『新增訂單』按鈕。」 |
| **祈使句、動詞開頭** | 用「點擊／輸入／捲動到／關閉」起頭 | 「這時候應該要能看到列表」 | 「捲動到頁面底部。」 |
| **主動語態** | 說「你做什麼」，不說「什麼被做」 | 「訂單會被建立」 | 「清單最上方出現一列『測試A』。」 |
| **同一物件全程同一名稱** | 元件名稱鎖定一次就不再改口 | 一下「儲存鈕」一下「送出鈕」 | 全程「『儲存』按鈕」 |
| **短句** | 一句以 20 字為度 | 「在確認所有欄位都填寫完成之後再按下位於右下角的那個藍色按鈕」 | 「填完所有欄位。<br>點擊右下角的『儲存』按鈕。」 |
| **禁用模糊詞** | 不寫「適當地」「正常」「應該」「檢查一下」「大致上」 | 「確認畫面顯示正常」 | 「確認金額欄顯示 `NT$ 1,200`。」 |
| **條件在前、動作在後** | 先講什麼情況，再講做什麼 | 「點擊重試，如果出現錯誤訊息的話」 | 「若出現『連線失敗』，點擊『重試』。」 |
| **預期結果可觀察** | 只寫看得見的文字、數字、狀態變化 | 「資料有正確寫入」 | 「重新整理頁面。該列仍然存在。」 |
| **前提寫在步驟之前** | 帳號、種子資料、必要開關列在最前面 | 把「要先登入」藏在第 4 步括號裡 | 「前提：已用 dev@example.com 登入。」 |

**還要加兩件 STE100 沒有、但驗收清單必須有的東西：**

1. **每一項標明對應的驗收條件**（`票券 AC-2`）。使用者才知道這一項不過代表什麼沒做到。
2. **每一項寫「不符時請回報什麼」**。不寫的話回報會變成「怪怪的」，pane 補正時只能猜。要具體到「錯誤訊息全文」「DevTools Console 的紅色訊息」「你當時點了哪個按鈕」。

**清單長度守則**：只列 **pane 沒有也無法自動驗到的東西**。純函式邏輯已經有 `verify:*` 腳本守著，再叫使用者手動點一次是浪費他的時間。**一張票 3～6 項是健康的**；超過 8 項通常代表這張票該拆，或代表自動化驗證欠太多——後者要在 RESULT.md 講明。

## 清單模板

pane 寫進 `RESULT.md` 的「## 人工驗收清單」段落，格式如下：

```markdown
## 人工驗收清單

測試頁已開啟：http://localhost:5174/orders
前提：已用 dev@example.com / dev1234 登入。種子資料含 3 筆訂單。
本清單只列自動化驗不到的畫面行為，共 4 項，預估 3 分鐘。

### V1 新增訂單後，列表立即出現該筆（票券 AC-2）
1. 點擊右上角的「新增訂單」按鈕。
2. 在「客戶名稱」欄輸入 `測試A`。
3. 在「金額」欄輸入 `1200`。
4. 點擊「儲存」按鈕。

預期：對話框關閉。清單最上方出現一列「測試A」，金額欄顯示 `NT$ 1,200`。
不符時請回報：畫面上的錯誤訊息全文，以及 DevTools Console 的紅色訊息。

### V2 重新整理後該筆仍在（票券 AC-2）
1. 按 F5 重新整理頁面。

預期：「測試A」那一列仍然存在。
不符時請回報：重新整理後清單的前三列各是什麼。

### V3 金額欄拒收非數字（票券 AC-4）
1. 點擊「新增訂單」按鈕。
2. 在「金額」欄輸入 `abc`。
3. 點擊「儲存」按鈕。

預期：對話框不關閉。金額欄下方出現紅字「請輸入數字」。
不符時請回報：對話框是否關閉、以及有沒有新增出一列。

### V4 窄視窗下表格可橫向捲動（票券 AC-5，我完全沒驗）
1. 把瀏覽器視窗拉窄到 400 px 以下。
2. 在表格上向左滑動。

預期：表格自己橫向捲動。頁面本身不出現橫向捲軸。
不符時請回報：截一張圖。
```

**每一項的標題就是「要驗什麼」的一句話結論**，使用者掃標題就知道這份清單涵蓋了什麼。**pane 自己沒驗過的項目要在標題標出來**（如 V4 的「我完全沒驗」）——那是它欠的債，不是使用者的例行工作，標出來使用者才會知道該多看兩眼。

## 主控回收時怎麼用這份清單

**1. `wait` 返回後、審碼的同時，把清單原樣搬進對話。** 不要摘要成「請驗一下訂單功能」——那等於把 pane 寫好的精確步驟丟掉。搬的時候補一句「頁面已經幫你開在 http://localhost:5174/orders」。

**2. 一波多票就標清楚哪個 port 屬於哪張票。** 使用者面前會同時有三個分頁，標題長得很像。

```
PROJ-111 訂單列表 → http://localhost:5173/orders （4 項，約 3 分鐘）
PROJ-112 設定頁   → http://localhost:5174/settings（3 項，約 2 分鐘）
```

**3. 使用者回報不符項，就 `herdr agent prompt` 回原 pane 補正。** 帶上他的原話——不要轉譯成你認為的技術問題，你的轉譯會把症狀的關鍵細節磨掉。補正後要求 pane **重跑該項並更新 RESULT.md 的對應條目**，然後你再請使用者只驗那一項。

**4. 驗收結果收錄進整合註解。** 在 `## 整合與複查（主控）` 裡加一段：

```markdown
**人工驗收**：4 項，使用者實驗 3 項通過，V4（窄視窗橫向捲動）未驗。
V3 第一次不符（對話框仍然關閉），已回 pane 修正並複驗通過。
```

**未驗的項目原樣留在「仍未驗證」段。** 使用者沒驗到的東西不會因為合併成功就變成驗過了。

**5. 使用者說「先不驗，直接合」也照辦**，但整合註解要寫「人工驗收清單已產出，使用者選擇不驗，全 N 項均為未驗證」。**選擇跳過是他的權利，紀錄失真不是。**

## 反模式

| 別做 | 為什麼 |
| --- | --- |
| 讓 pane 自己挑 port | 兩個 pane 撞同一個 port，使用者看到的畫面會屬於錯的那張票，而畫面「看起來是對的」 |
| 固定 `sleep 10` 就開頁 | 冷啟動慢就開到空白頁，使用者會以為功能壞了 |
| server 起不來還是硬開一個網址 | 404 比不開更糟，使用者會把環境問題誤判成功能問題 |
| 驗收還沒回覆就 `git worktree remove` | worktree 一刪 server 的 cwd 就沒了，使用者手上的頁面當場壞掉 |
| 主控自己重寫一份清單 | 你沒改過那些碼，寫出來的是通則不是這張票的具體行為 |
| 清單裡寫「確認顯示正常」 | 「正常」是模糊詞，使用者不知道該看哪裡，回報也會變成「怪怪的」 |
| 把已被 `verify:*` 守住的邏輯也列進清單 | 浪費使用者的時間，而且會稀釋真正需要人眼的那幾項 |
| 一張票列 15 項 | 沒人會驗完。那代表票該拆，或自動化驗證欠太多 |
| pane 沒驗過的項目不標出來 | 使用者會用例行心態掃過，而那正是最可能壞的地方 |
| 把使用者的回報轉譯成技術描述再丟給 pane | 症狀的關鍵細節會在轉譯時被磨掉，pane 只能猜 |
| 使用者跳過驗收就把該項寫成通過 | 紀錄失真比沒驗更危險，未來回查會被誤導 |

## 兩支 skill 的差異

| | `herdr-claude-wave` | `herdr-codex-wave` |
| --- | --- | --- |
| 誰執行開頁 | Claude pane（`--permission-mode auto`；`open` 與 `nohup` 可能撞權限提示，要預先補進 worktree 的 `.claude/settings.local.json` 白名單） | Codex pane（Yolo Mode 無關卡，直接跑） |
| 清單的證據力 | pane 與主控同模型，**清單裡「我已驗過」那幾項證據力偏低**，主控要抽驗一項 | 異質來源，證據力較高 |
| 失敗回收 | `herdr agent prompt` 補正，同 pane 保留脈絡 | 同左 |
