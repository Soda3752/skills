# 常駐 pane：reviewer 與 verifier

v2 從主控身上搬走兩件事：**讀 diff 審碼**（最大的 context 消耗）與**整合後跑閘門**（最大的等待）。兩者都外包給跨波次活著的常駐 pane。

## 為什麼是常駐而不是每波開

實作 pane 是**一票一個、用完就關**，因為它的脈絡就是那張票，帶不到下一張。

常駐 pane 相反，它的價值全部來自累積：

| 累積什麼 | 第二波開始就有的效果 |
| --- | --- |
| 這個 repo 的慣例（命名、分層、既有模式） | 判斷「超出票面範圍」時不必重新摸索什麼叫正常 |
| 哪些閘門本來就紅、為什麼 | 不會把已知排除項當成回歸來報 |
| 上一波抓到什麼、怎麼處置的 | 同類問題第二次出現時直接指出「這與波 2 的 PROJ-13 是同一種」 |
| 基準線斷言數 | 回歸偵測的對照組，不用每次重新量 |

每波重開等於每波重新學一次，而學習成本正好落在最不該花時間的地方。

**代價是 context 會累積。** 見[生命週期與換手](#生命週期與換手)。

## reviewer

### 職責邊界

reviewer 做**可以靠讀碼與跑指令完成的判斷**；需要全局視野或需要下決定的事留給主控。

| reviewer 做 | 主控做 |
| --- | --- |
| 逐行讀 diff | 決定阻斷級問題要退回還是接受 |
| 找出超出票面範圍的改動，判斷必要或順手 | 判斷「落在被排除閘門盲區」的風險 |
| 檢查 gitignored 檔有沒有被 commit | 地基票的補測 |
| 讀 log 實際結尾，確認測試真的跑過、數斷言數 | 把結論寫進整合註解 |
| 反向舉證：給出會讓它壞掉的輸入 | 決定要不要動用 Codex 對抗複查 |

**reviewer 不改任何檔案。** 它是唯讀角色，發現問題就回報，補正一律由原實作 pane 做——那個 pane 還握著完整脈絡，而 reviewer 只看得到 diff。

### 開場指令模板

起 pane 之後送這一則，之後每張票只送短的派工（見下）。

```markdown
你是這一輪多波開發的常駐 code reviewer。你會在整個流程中活著，每張票完工後我會派你審它的 diff。

## 你的角色

只讀不寫。你不改任何檔案、不 commit、不動 git 狀態、不碰 Linear。發現問題就回報給我，補正由原實作 pane 做——它握有完整脈絡，你只看得到 diff。

## 專案

- 主 repo：<絕對路徑>
- worktree 根目錄：<絕對路徑>（每張票一個子目錄）
- base 分支：<分支名>
- 技術棧：<一句話>
- 專案指令在主 repo 的 CLAUDE.md，先讀一遍。

## 已知的閘門真相（重要）

實跑驗證過的結果，不是設定檔宣稱的：

- 可用閘門：<列出來>
- **本來就紅的**：<列出來，含真因>。看到這些不要當成回歸來報。

## 每張票我會給你什麼

票號、worktree 路徑、base 分支。票上的規格你自己用 Linear MCP 讀（`get_issue` + `list_comments`，解鎖註解裡有上游的坑）。`RESULT.md` 在 worktree 根目錄，那是實作 pane 的自述。

## 你要做的六件事

1. **`git -C <worktree> diff <base>...HEAD` 逐行讀完。** 不要只看 `--stat`。
2. **範圍核對**：有沒有超出票面的改動？**判準不是「有沒有超出」而是「有沒有正當理由」。** 逐行比對——若拆檔前後只差一個函式名，那是忠實搬移不是偷渡重構，風險警示可以解除。
3. **`git -C <worktree> status --short`**：有沒有 gitignored 檔被 commit、工作區乾不乾淨。
4. **測試真的跑過嗎**：讀 build log 的實際結尾，數斷言數。**測試沒被執行也會 exit 0**，只看 exit code 會被騙。
5. **反向舉證**：對每個你打算寫「沒問題」的結論，先試著**給出一組會讓它壞掉的輸入**。舉不出來才算過。這一條比任何 checklist 有效。
6. **`RESULT.md` 對帳**：它宣稱的驗收結果與你讀到的碼一致嗎？特別注意它寫「通過」但你找不到證據的項目。

## 回報格式（固定，我靠這個分流）

<回報格式見下方，原樣貼進指令>

## 不要做的事

- 不要改檔案、不要 commit、不要 rebase、不要動 Linear
- 不要把「編譯過」當成驗收通過
- 不要重述 RESULT.md——我讀得到，你的價值在它沒寫或寫錯的地方
- 不要為了顯得有產出而報無關緊要的風格問題。**沒發現就說沒發現**
```

### 逐票派工指令

開場指令送過一次之後，每張票只要這麼短：

```bash
herdr agent prompt reviewer "審 PROJ-111。worktree: <路徑>，base: <分支>。RESULT.md 已寫。這是地基票，下游有 3 張會直接用它的型別定義——請對型別邊界特別嚴，並跑一輪 codex:rescue 對抗複查，明講『請證明這段是錯的』。"
```

**每次都要帶的**：票號、worktree 路徑、base 分支。

**視情況帶的**：這張票是不是地基票、有沒有下游、要不要動用 Codex 對抗複查、上一波有沒有同類問題。

### 回報格式

要求 reviewer 用固定三級回報，主控靠它分流：

```markdown
## 審碼結果：PROJ-111

**結論**：阻斷 / 有建議 / 通過

### 阻斷級（必須退回補正）
- <問題> → <會怎麼壞：具體到輸入與後果>
（沒有就寫「無」）

### 建議級（可以合，但主控應該知道）
- <問題> → <為什麼不阻斷>

### 反向舉證
- <我試圖找出會讓它壞掉的輸入，結果：找到 / 找不到>

### 範圍核對
- 票面內：<檔案數>
- 超出票面：<檔案清單> → <判定：必要 / 順手 / 可疑> + <逐行比對的依據>

### 測試證據
- 指令：<實際跑的>
- 結尾：<log 的實際最後幾行>
- 斷言數：<數字>（基準線 <數字>）

### RESULT.md 對帳
- 它宣稱通過但我找不到證據的項目：<清單，沒有就寫無>
```

**「通過」這個結論要有代價。** 指令裡要寫明：reviewer 回「通過」而主控事後發現阻斷級問題，那是 reviewer 的失誤——讓它知道這一點，它就不會為了省事而放行。

### reviewer 是 Claude，這件事沒有解決同盲點

pane 是 Claude、reviewer 是 Claude、主控也是 Claude。**換一個 pane 消除的是「自己審自己」那層偏誤，不是模型層的盲點。**

所以 v1 的三個補救手段仍然全部適用，至少用一個：Codex 對抗複查（最強，寫進 reviewer 的逐票指令）、執行證據取代判斷、反向舉證式自審（已經寫進協定）。

## verifier

### 職責邊界

verifier 只做一件事：**在 base 分支上跑完整閘門，回報結果與斷言數。**

它不讀 diff、不判斷對錯、不碰 Linear。**它的價值在「主控不必等」**，不在判斷力。

### 開場指令模板

```markdown
你是這一輪多波開發的常駐 verifier。你會在整個流程中活著，每一波全部合併完之後我會派你跑閘門。

## 你的角色

只跑不改。你不改任何檔案、不 commit、不 rebase、不碰 Linear。跑完回報數字，判斷由我做。

## 專案

- 主 repo：<絕對路徑>（你的 cwd，你只在這裡工作）
- base 分支：<分支名>

## 閘門（實跑驗證過的真相，不是設定檔宣稱的）

- 要跑的：<逐條列出完整指令>
- **不要跑、也不要修的**：<逐條列出 + 真因>。這些本來就紅，與這一波無關。

## 基準線

- 上一次的數字：<N suites / M tests / 0 failures>
- 這是你的對照組。**斷言數變少是最嚴重的訊號**，比紅燈更嚴重——紅燈看得見，測試消失看不見。

## 每次我會給你什麼

波次編號、這一波合了哪幾張票（ff commit hash）、當前基準線數字。

## 你要做的四件事

1. `git -C <主 repo> log --oneline -<N>` 確認那幾個 ff commit 真的在 HEAD 上。**不在就直接回報，不要繼續跑。**
2. 逐條跑閘門，**輸出重導到 log 檔再 tail**，不要讓數千行進你的 context。
3. **數斷言數**：讀 test-results XML 或 log 的統計行，不要只看 `BUILD SUCCESSFUL`——測試沒被執行也會 exit 0。
4. 與基準線比對，用下面的格式回報。

## 回報格式（固定）

<見下方>

## 不要做的事

- 不要修任何紅燈，即使你看得出怎麼修
- 不要跑「不要跑」清單裡的閘門
- 不要把 `BUILD SUCCESSFUL` 當成測試跑過
- 不要猜是哪張票造成的——回報事實，二分由我做
```

### 逐波派工指令

```bash
herdr agent prompt verifier "波 2 驗證。已合進 <base> 的 ff commit：a1b2c3d(PROJ-12) / e4f5g6h(PROJ-13) / i7j8k9l(PROJ-17)。基準線 50 suites / 457 tests / 0 failures。"
```

### 回報格式

```markdown
## 驗證結果：波 2

**結論**：綠 / 紅（已知排除項）/ 紅（新問題）/ **斷言數異常**

### commit 確認
- a1b2c3d / e4f5g6h / i7j8k9l 均在 HEAD 上：是 / 否

### 逐條閘門
| 指令 | 結果 | 耗時 |
| --- | --- | --- |
| ./gradlew :composeApp:assembleDebug | 通過 | 1m12s |
| ./gradlew :composeApp:testDebugUnitTest | 通過 | 3m40s |

### 斷言數
- 本次：50 suites / 457 tests / 0 failures
- 基準：50 suites / 457 tests / 0 failures
- 差異：無 / **少了 N 個 test（回歸訊號）**

### 紅燈明細（有才寫）
- <指令>：<log 的實際錯誤，原文不要摘要>
```

### 主控收到紅燈時的處置順序

1. **是不是已知排除項** → 是就忽略，並回頭修正 verifier 開場指令裡的排除清單（它漏了）
2. **是不是斷言數變少** → 是就**停下來**。這是唯一必須中斷多波推進的紅燈：base 現在是壞的，往上疊只會擴大污染面
3. **二分是哪一張票** → 每張票都是一個 ff commit，`git bisect` 或逐個 `git reset --hard HEAD~1` 都能定位。定位到就回原 pane 補正

## 生命週期與換手

### 什麼時候起

第 2 步「開工前置」的第六件，**在第一波派工之前**。它們要能在第一張票完工的當下就接手，晚起等於第一波白費。

### 什麼時候換

**每波收完檢查一次兩隻的 context 用量。超過 60% 就換一隻。**

換的做法不是重開一張白紙，而是**把累積的知識寫進新 pane 的開場指令**：

```markdown
（原本的開場指令）

## 前一任 reviewer 累積的專案知識

- 這個 repo 的 ViewModel 慣例是 <...>，看到偏離要問
- 波 2 的 PROJ-13 出現過「拆檔時順手改函式簽名」，判定為必要（逐行比對只差名字）
- `:composeApp:allTests` 本來就紅（iOS 缺 Lottie SPM），實際閘門是 `testDebugUnitTest`
- 基準線：50 suites / 457 tests
```

**這段知識轉移是換手唯一有價值的部分。** 少了它，換手就等於把常駐的好處還回去。

### 什麼時候關

**全部波次收斂、收工回報寫完之後**。不要在最後一波合併完就關——收工回報裡的未驗證總清單、閘門邊界說明，都可能需要回頭問它們。

```bash
herdr workspace close <reviewer workspace id>
herdr workspace close <verifier workspace id>
```

## 反模式

| 別做 | 為什麼 |
| --- | --- |
| 讓 reviewer 改檔案 | 它只看得到 diff，沒有實作 pane 的脈絡；改出來的東西往往在別處壞掉 |
| 讓 verifier 修紅燈 | 同上，而且它會把「已知排除項」也一起修掉，破壞閘門邊界 |
| 每波重開常駐 pane | 累積的專案知識是它們的全部價值 |
| 換手時只重開不轉移知識 | 等於把常駐的好處還回去 |
| 把 reviewer / verifier 加進 `herdr agent wait` | 它們在波次之間是 idle，Monitor 會立刻返回 |
| reviewer 回報時重述 RESULT.md | 主控讀得到，價值在它沒寫或寫錯的地方 |
| reviewer 為了顯得有產出而報風格問題 | 稀釋真問題的訊號，主控會開始略讀它的回報 |
| 沒給 reviewer「已知本來就紅」的清單 | 它會把排除項當回歸報，每一波都報一次 |
| verifier 只看 `BUILD SUCCESSFUL` | 測試沒被執行也會 exit 0 |
| 斷言數變少還繼續開下一波 | 這是唯一必須停的紅燈 |
| 最後一波合完就關掉常駐 pane | 收工回報還可能需要回頭問它們 |
