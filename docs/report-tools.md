# report-tools

產生繁體中文報告。

## 作用

這個 plugin 有兩個 skill。它們把技術內容轉成非工程角色看得懂的文件。

| Skill | 輸入 | 輸出 | 讀者 |
| --- | --- | --- | --- |
| `pm_report` | 剛完成的程式碼調查 | 技術報告，含流程圖 | PM、技術主管 |
| `whats-new` | 兩個版本號 | 版本更新說明 | 使用者、客戶 |

兩個 skill 都不需要票券系統。它們在任何專案都能用。

## 安裝

```
/plugin marketplace add Soda3752/skills
/plugin install report-tools@soda-skills
```

## pm_report

### 作用

它把對話中**剛完成的調查結果**整理成一份結構化的繁體中文技術報告。

它不重新調查。它整理你和 Claude 剛才討論出來的內容。

### 使用方式

調查告一段落後，說：

```
整理成報告
幫我寫報告
產生報告
整理業務邏輯
幫我把這些整理好
```

說法不正式也會觸發。只要對話中有剛完成的分析結果就可以。

### 它不會問你問題

它從對話上下文自己抓四件事：

1. 調查主題是什麼。
2. 涉及哪些檔案、函式、類別。
3. 業務流程怎麼走。
4. 發現了哪些風險。

### 報告結構

固定七章：

```
一、結論摘要
二、涉及檔案清單
三、整體業務流程      ← Mermaid 流程圖
四、各層機制詳細說明
五、各層效果彙整
六、潛在風險與邊界情境
七、相關設定常數（若有）
```

### 最重要的規則：程式碼識別字要翻譯

報告的讀者可能不寫程式。所以變數名、函式名、參數名**一律翻譯成中文描述**。

| 翻譯原則 | 範例 |
| --- | --- |
| 布林旗標 → 「是否 + 動詞」 | `isCurrentlyMoving` → 是否正在移動中 |
| 數值門檻 → 「X 上限」或「X 下限」 | `accuracyLimit` → 精度上限 |
| 計數器 → 「X 次數」 | `failThreshold` → 失敗次數門檻 |
| 函式名 → 動詞片語 | `uploadLocation()` → 位置上傳函式 |
| 系統 API 屬性 → 中文意義 | `distanceFilter` → 距離篩選器 |

**這四類不翻譯：**

- 類別名稱（`CLLocationManager`、`CMMotionManager`）
- API 路徑字串（`api/upload/location`）
- 業界通用縮寫（GPS、API、UI、HTTP、JSON）
- 程式語言關鍵字

### 流程圖規範

- 主業務流程用 `flowchart TD`。
- 狀態轉換用 `stateDiagram-v2`。
- 節點文字**全部用繁體中文**。
- 決策節點必須寫明條件。不可以含糊。
- 換行用 `<br/>`。**不要用 `\n`。**

### 儲存位置

```
.claude/report/YYYY_MM_DD/{主題}報告.md
```

日期是今天。檔名用報告主題命名，例如 `GPS位置上傳業務邏輯調查報告.md`。

存檔後它會告訴你路徑，並附一段兩三句話的摘要。

### 存檔前的檢查

它自己檢查五項：

- [ ] 結論摘要直接回答問題，不迴避。
- [ ] 所有流程圖節點都是繁體中文。
- [ ] 正文沒有任何英文變數名。
- [ ] 風險區塊至少有兩個真實的邊界情境。
- [ ] 報告存在正確的日期資料夾。

## whats-new

### 作用

它產生兩個版本之間的更新說明。

它**完全從使用者體驗的角度**描述。它不提程式碼、函式名稱、變數、檔案路徑。

### 使用方式

給它兩個版本號。舊的在前，新的在後：

```
0.1.5 0.1.6
```

或直接說：

```
產生 What's New
整理版本更新內容
幫我做 release notes
從 0.1.5 到 0.1.6 有什麼更新
```

### 它怎麼找版本範圍

它依序嘗試三種方式：

1. **比對 git tag。** 找包含版本號的 tag，例如 `v0.1.5`、`0.1.5`、`release/0.1.5`。
2. **從 commit message 找。** 沒有 tag 時，搜尋「更新版本 0.1.5」或「version 0.1.5」這類 commit。
3. **問你。** 前兩種都找不到時，它請你確認正確的範圍。

### 它怎麼分析

找到範圍後，它把 commit 分類，再**平行派遣多個 agent** 深度分析每個 commit。最後整合成一份報告。

平行分析的原因是：一個版本可能有幾十個 commit。逐一分析太慢。

### 輸出結構

三章：

```
## 新增功能
## Bug 修復
## 基礎建設
```

「基礎建設」章節說明使用者感受不到、但影響穩定性的改動。

### 語氣規則

從使用者的角度寫。

**寫這樣：**

> 匯出報表時可以選擇日期範圍了。

**不要寫這樣：**

> 在 `ExportService.kt` 新增 `dateRange` 參數。

第二種寫法對使用者沒有意義。
